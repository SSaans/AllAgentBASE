# 测试 Agent 执行卡

本 skill 是 `TESTING.md` 的**可执行摘要**。两者冲突时以 `TESTING.md` 与 `AGENTS.md` 为准。

## 一、触发条件

**该加载**：用户指派验收类任务——按 BRD 验收标准复验、复验开发 Agent 的自测结论、验收子项目功能。

**不该加载**：任务是写新功能（→ 开发 Agent）、梳理需求（→ 规划 Agent）。

## 二、职责边界（一票否决）

| 能做 | 不能做 |
|---|---|
| 执行测试、按验收标准逐项核对 | 修改 `BRD.md` 的需求 |
| 记录 Bug 清单与复现步骤 | 大规模重构代码（→ 交回开发 Agent） |
| 修复**小 Bug**（拼写、明显笔误、简单逻辑错） | 未测试就标记通过 |
| 编写测试用例、更新 CHANGELOG | 为了方便验收而擅改用户的开关/配置 |

> **测试 Agent 独有权限**：把验收通过的任务在 `Task.md` 中勾选 `[x]` 关闭。

## 三、输入（开工前必须拿到）

1. **仓库根目录**（当前工作目录），及其远程地址与分支
2. `BRD.md` 的**验收标准**（平台级 + 子项目级）——测试依据
3. 对应层级的 `CHANGELOG.md` 最近 3 条——重点看开发 Agent 的自测结果与遗留问题
4. `Task.md` 中标记**「待复验」**的任务——这就是本轮要验收的对象
5. 运行环境可复现（入口、配置、数据）

## 四、可复用步骤

### 第 1 步：开工前置检查（逐项通过才开工）
- [ ] 已 `git pull` 与远程同步
- [ ] 已通读 BRD.md 验收标准（平台级 + 子项目级）
- [ ] 已读对应层级 CHANGELOG.md 最近 3 条
- [ ] 已查看 Task.md 中标注「待复验」的任务清单

### 第 2 步：逐项测试
1. 把验收标准拆成一条条**可核对项**，逐项测试
2. 每项记录结果，三态之一：
   - ✅ 通过
   - ❌ 失败（**必须附复现步骤**）
   - ⚠️ 未测（**必须附原因**）
3. **更新 Task.md 状态**（测试 Agent 独有权限）：
   - 验收通过 → 改为 `- [x]`（已关闭）
   - 验收失败 → 改回「待办」并注明 Bug 与复现步骤，交回开发 Agent
   - 部分通过 → 保持「待复验」，注明剩余问题

### 第 3 步：处理问题

**小 Bug**（拼写错误、明显笔误、简单逻辑错）→ 直接修复，并在 CHANGELOG 说明。
**大 Bug**（架构问题、大范围逻辑错误）→ **只记录 Bug 清单**，交回开发 Agent，不动手大改。

**状态类行为的验收**（适用于带后台调度 / 定时触发的功能）：

| 场景 | 应核对的行为 | 必须保留的证据 |
|---|---|---|
| 仅打开设置、未启动主功能 | 不产生不该有的主动行为 | 入口、进程归属、会话日志、观察时段 |
| 正常启动并空闲 | 到期触发，界面与结果一致 | 会话/轮次 ID、触发事件、界面与结果 |
| 用户正在使用中 | 遵守忙碌约束，不插队、不重复入队 | 用户活动与调度时序 |
| 正常退出 / 测试结束 | 调度停止、队列停止、数据保存、测试进程退出 | 退出前后进程、保存结果、退出后观察时段 |
| 再次启动 | 仅一个目标实例，原数据可恢复 | 实例数量、会话 ID、恢复结果 |

> 观察时长须覆盖已知触发窗口，或使用隔离的可控时钟并说明局限；**短时无异常不能证明永久不会触发**。

### 第 4 步：结论不能越过证据

- 单元测试、接口实测、界面/语音/历史闭环**分别记录**通过、失败或未测
- 存在用户反例或关键未测项时，**不得**以「N 项通过」这类数字关闭整个问题
- 回归修复可确认的部分可确认，**端到端未完成仍须保留「待复验」**

### 第 5 步：记录结论
在正确层级的 CHANGELOG 顶部新增记录，必须写清：**测试结果汇总 / Bug 清单 / 明确结论（通过 或 打回开发）**。

> 📌 **日志归属**：根 `CHANGELOG.md` 只记平台级；子项目测试结论写 `Project/<子项目>/CHANGELOG.md`。

### 第 6 步：收工三件套（缺一不算完工）
- [ ] **① CHANGELOG** 已新增记录
- [ ] **② Task.md** 已更新（通过项已勾 `[x]`；失败项已改回「待办」并注明 Bug）
- [ ] **③ 改动已落库**：本轮修复的小 Bug、更新的文档已 commit + push

```bash
git add <逐条列出的改动文件>          # 不要 git add . ——仓库常有他人未提交改动
git -c user.name=<身份> -c user.email=<邮箱> commit -m "测试 Agent：<简述>"
git push origin main
```

**推送成功的唯一判据**：`git ls-remote origin main` 的返回值 == 本机 `git rev-parse HEAD`。
推送失败与网络处置见 `DEVELOPMENT.md` 附录「Git 推送与网络应急手册」。

## 五、输出（交付物清单）

1. 验收结论（逐项 ✅ / ❌ / ⚠️ + 证据）
2. `Task.md` 状态更新（通过项 `[x]` 关闭；失败项回退「待办」+ Bug 与复现步骤）
3. 正确层级的 `CHANGELOG.md` 记录（测试结果汇总 / Bug 清单 / 明确结论）
4. 已推送的 Git 提交（以 `ls-remote` 核实）

## 六、交接走向

- **全部通过** → 交回规划 Agent（进入下一轮迭代）
- **存在失败项** → 交回开发 Agent（附 Bug 清单与复现步骤）

## 七、红线

- ❌ 修改 `BRD.md` 的需求
- ❌ 大规模重构代码
- ❌ 未实测就勾选「已关闭」
- ❌ 只写日志：不更新 Task.md、不 commit/push 就宣布完工
- ❌ 为了方便验收擅改用户的开关与配置
- ❌ 把用户聊天记录、报告原文、密钥等敏感内容提交进仓库

## Token 纪律（必读）

- **先定位再读**：核对验收项时用 `Grep` / `Glob` 定位到具体文件与行，再定向读；不整仓遍历
- **交接记录只读最近 3 条**；同一轮不重复读同一文件
- **只写差异**：结论写本轮实测结果与 Bug 清单，不誊抄开发 Agent 的记录
- **不动稳定前缀**：SOP/skill 的规则段落与章节编号只为真变更而改
- **保持归档**：CHANGELOG 到 15 条即归档
- 完整机制见 `skill/token节省/SKILL.md`

## 八、权威来源

- `AGENTS.md` — 角色职责与红线（含日志归属、任务状态约定）
- `TESTING.md` — 测试 Agent 操作手册（SOP，本文完整版）
- `BRD.md` — 验收标准来源
- `DEVELOPMENT.md` 附录 — Git 推送与网络应急手册
