# Token 节省与缓存友好执行卡

## 一、触发条件

**该加载**：要在本仓库做大范围读写（通读文档、扫描代码、整理日志、写交接），或用户提到省 token、缓存、成本、上下文过长。

**核心命题**：本仓库是**纯文档协作仓库**，没有运行时服务宿主。因此「运行时 prompt 缓存」的多数手段**不能直接落地**，但有**等价替代**——落点是①**文档结构**②**Agent 的读写顺序**。下面逐条给出映射，能落地的直接写细。

## 二、逐条落地判定（先看这张表）

| 理论手段 | 本仓库能否落地 | 落地方式 / 等价替代 |
|---|---|---|
| **① 1h 缓存块**（固定不变内容标记缓存，内容必须逐字节一致才命中） | ⚠️ 无运行时标记，**但可等价** | 文档/skill 的**稳定前缀**就是缓存块：把不变内容集中在**头部固定区**，易变内容（日期、状态、任务进度）放**尾部**。这样每轮只有尾部变动，头部逐字节稳定 → 上游若做前缀缓存即可命中 |
| **② 多模型分工 / 内容分流** | ✅ 部分 | 映射为**任务分流**：简单查找（找一行、查一个文件名）只用 Grep/Glob **定位**，不启动全量通读；复杂任务（规划、勘误、立项）才通读全文。判据＝**关键词命中即可回答＝轻**，需跨文档推理＝重 |
| **③ 滑动窗口 + 分段缓存** | ✅ **已在用** | 就是 CHANGELOG 的 **15 条上限 + `CHANGELOG.archive.md` 归档**机制。分层对应：最新条目＝不缓存区，紧邻条目＝短期区，归档＝压缩区 |
| **④ 记忆召回 + 窗口缩减到约 30 条** | ✅ 部分 | 映射为**按需定向读**：先用 Grep 定位再读命中的段落（`offset`/`limit`），**只读最近 3 条交接记录**，禁止一次性读全量 CHANGELOG／全仓递归扫描 |
| **⑤ 分层缓存**（system 1h / 旧摘要 30min / 近 10 条 5min / 最新 3 条不缓存） | ✅ 可落地为**文档分层** | 见下方「三、文档三层结构」 |
| **固定前缀策略** | ✅ | skill 的 frontmatter 字段名与顺序保持稳定；SOP 章节编号与标题不随意重排；新增内容**追加**而非插入中段 |
| **每 20 条生成摘要** | ✅ **已在用** | 归档即摘要化：移入 archive 时保留标题与结论要点，正文细节留在归档文件里，不进常读区 |
| **时间敏感信息单独放置** | ✅ | 日期、状态行、进度数字统一放**独立的头部/尾部行**，不与正文混排——改它不动正文（正文那份就仍是稳定前缀） |
| **工具定义也缓存** | ✅ | skill 的 `name` / `description` / `trigger` 一旦定下就**不轻易改**；改了等于让上游所有缓存失效，只在必要时改 |
| **向量数据库召回记忆** | ❌ 不适用 | 本仓库无运行时向量库。等价替代＝**Grep 即召回**：用关键词在仓库内检索，命中即读，不把整仓塞进上下文 |
| **消息分类器（文字/图片/指令）** | ❌ 不适用 | 本仓库不处理用户消息流。等价替代＝**任务分类器**（见 ② ） |

## 三、文档三层结构（分层缓存的落地写法）

任何本仓库文档（SOP、skill、BRD、Task）都按三层组织，**读写时只碰需要的那层**：

| 层 | 内容 | 变动频率 | 读写建议 |
|---|---|---|---|
| **L1 稳定层** | 角色定义、职责边界、红线、流程步骤、接口契约 | 几乎不变 | 首读一次即可；**改写时尽量避免动它**，动了等于让前缀缓存全部失效 |
| **L2 半稳定层** | 文档骨架、章节标题、任务清单条目、验收标准条目 | 偶尔新增 | 用 Edit **追加**新条目，不重排既有条目 |
| **L3 易变层** | 日期、当前状态行、进度数字、CHANGELOG 顶部新记录、Task.md 状态标记 | 每次变动 | 集中放在**头部状态区或文末**，与 L1 正文物理隔开 |

> **为什么值钱**：L1 逐字节稳定 ⇒ 上游对「文档前缀 + skill 正文」的缓存能持续命中；只有 L3 变化 ⇒ 每轮实际新增的计算量被压到最小。**把 L1 内容搬到文档中段、或为了"更好看"重排章节，是直接烧钱**。

## 四、省 Token 十条纪律（读文档场景，逐条可执行）

1. **先定位，再读**：任何"找东西"的任务，先 `Grep` / `Glob` 拿路径与行号，再定向 `Read`。**禁止**无明确目标就递归遍历目录、逐个读文件。
2. **长文档只用窗口读**：`Read` 带 `offset` / `limit` 只取需要的段落；不为了"看全貌"把几千行文档整读进上下文。
3. **交接记录只读最近 3 条**：这是全平台通行约定（`AGENTS.md` 已写死）。**不要**通读全量 CHANGELOG——历史细节在归档里，需要时再定点取。
4. **同一轮内不重复读同一文件**：内容已在上下文里就不再读一遍；要引用就引用，不要复制粘贴长段。
5. **只写差异，不誊抄**：写 CHANGELOG、写交接、写结论时写**本轮新增与变化**；不要把已有文档的原文抄一遍。改动旧记录时用 Edit 最小替换，不重写整段。
6. **skill 与 SOP 之间用指针，不复制全文**：需要引用某规则就写"见 `PLANNING.md` 第 N 步"，**不要**把整段规则复制到第二个文件——重复内容会随每轮读取被反复计费。
7. **要点式记录，不写散文**：CHANGELOG 条目用短句 + 列表，一条记录控制在一屏内。长叙述不产生交接价值，只产生费用。
8. **保持归档机制运转**：根与子项目 CHANGELOG 各自 15 条上限，超出立即归档。**日志无上限膨胀 = 每轮都要读更长的文件**。
9. **稳定前缀不动**：`AGENTS.md` / 三本 SOP / skill 正文的 L1 段落，只在规则真变了才改。**避免"重排文档""统一格式"这类无功能收益的大改**。
10. **本地工具输出先落文件再读**：本机 PowerShell 的输出常不回传，反复试命令比"写文件 + 读一次"贵得多。**一次写文件、一次读**，不要连续重试同样命令。（Windows 环境专用，见 `DEVELOPMENT.md` 附录）

## 五、写文档时的缓存友好写法（正面清单）

- ✅ 新记录**追加**在文件顶部（CHANGELOG）或章节末尾（BRD/Task），**不插入中段**
- ✅ 状态行、日期行**独立成行**，放在头部状态区或文末，不与正文混排
- ✅ 章节标题与编号**保持稳定**，新增内容用新的小节号，不改动既有编号
- ✅ skill 的 `frontmatter` 字段名、顺序、`trigger` 词表一旦定下就保持稳定
- ✅ 长表格、长清单放**参考资料**（`references/`），正文只留结论与指针

## 六、失效红线（做了等于让缓存全废）

- ❌ 为"排版好看"重排章节顺序、改写标题措辞
- ❌ 把 L3 易变信息（日期、状态）插进 L1 正文中间
- ❌ 在多个文件里复制同一段长规则
- ❌ 每轮通读全量 CHANGELOG / 全仓文件
- ❌ 同一轮反复重试同一条本地命令
- ❌ 无上限地往 CHANGELOG 追加而不归档

## 七、开工自检（3 秒版）

动手前问自己三句：
1. 我要找的东西，**能不能先用 Grep 定位**？（能 → 别通读）
2. 我要写的东西，**是不是可以追加而不是改写**？（是 → 别动 L1）
3. 我上一轮是不是**已经读过这个文件**？（是 → 别重读）
