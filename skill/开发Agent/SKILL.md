# 开发 Agent 执行卡

本 skill 是 `agents/开发.md` 的**可执行摘要**。两者冲突时以 `agents/开发.md` 与 `AGENTS.md` 为准。

## 一、触发条件

**该加载**：用户指派实现类任务——按 change 的 tasks.md 逐条实现、写功能代码、修 Bug、部署子项目、搭开发环境。

**不该加载**：需求还在梳理阶段（→ 规划 Agent）。测试已并入本角色，不再往外推。

## 一·五、实现必须按 change 走（2026-10-27 新增）

**开工顺序**：`openspec status --change <name> --json` → 读 `proposal.md` / `specs/` / `design.md` / `tasks.md` → 按 `tasks.md` 逐条做。

- 每完成一条，在该文件对应行勾 `- [x]`，再跑 `openspec instructions apply --change <name> --json` 确认进度变了
- 规格不成立 → `openspec-update-change` 改产物，再改代码，**不许先斩后奏**
- 上下文快满 → 进度写进产物，开新窗口接着干
- 自己逐条对 Scenario 验完、写好验收结论，等用户点头后执行 `archive`

> 判据与两棒分工见根 `AGENTS.md`「📋 完整工作流程（SDD）」，这里只列动手顺序。

## 二、职责边界（一票否决）

| 能做 | 不能做 |
|---|---|
| 编写/修改代码文件、创建项目文件 | 修改 `openspec/specs/` 的**需求部分**（只能补充技术细节） |
| 安装依赖、跑本地基本功能自测 | 跳过自测就标记任务完成 |
| 勾 `tasks.md`、写交付说明、按场景验收 | 删掉失败的实测记录 |
| 当场登记新发现的 Bug（状态：待办） | 需求不明时自行猜测实现 |
| 临时脚本写进仓库外的 `H:\Program\_wb\` | 把探针 / 中间产物 / 输出写进仓库工作区 |
| 写验收结论（逐条对应 Scenario + 证据） | 没跑场景就写「通过」；替用户写他验过的结论 |

> 需求有歧义 → **停下**，记进 change，交回规划 Agent，**不许猜**。

## 三、输入（开工前必须拿到）

1. **仓库根目录**（当前工作目录）与其远程地址、分支
2. `openspec/specs/`（平台级 + 对应子项目级）——需求真相来源
3. 对应的 change——本轮要做的活；**没有 change 就停下，交回规划 Agent 立项**
4. 四件套已读齐：proposal / specs / design / tasks
5. 开发环境就绪（语言运行时、包管理器可用）

## 四、可复用步骤

### 第 1 步：开工前置检查（逐项通过才开工）
- [ ] 已 `git pull` 与远程同步
- [ ] **工作区核对**：当前目录是唯一权威工作区（`git remote -v` 指向本项目远程）；若发现本机存在**其他克隆副本**，先停下——把改动合并回主工作区，不要在多份副本里各改一半
- [ ] **交接证据三查**（防"证据留在别人本地"）：
  1. 远端是否有新提交：`git fetch origin`
  2. 本机其他克隆是否有未提交改动
  3. 运行目录实际配置与文档描述是否一致（配置档、进程、日志）
- [ ] 已通读 `openspec/specs/`（当前能力基线），只当背景
- [ ] 已读本次 change 的四件套
- [ ] **已拿到本次 change 并读齐四件套**：`openspec status --change <name> --json` → `proposal.md` / `specs/` / `design.md` / `tasks.md`
- [ ] 没有 change 就先立项；子项目没 init 就先在自己根 init（**不在仓库根 init**）
- [ ] 已确认本次 change 的 `tasks.md` 范围
- [ ] 开发环境就绪
- [ ] **临时文件写到仓库外**：探针 / 中间产物 / 输出一律放 `H:\Program\_wb\`，**不许落在仓库工作区**（仓库根同时是工作区根，写进来就会被当成项目文件，等着被误提交）

### 第 2 步：开发
1. 开工时确认 `openspec status --change <name>` 没被标阻塞，并写下本轮要做哪几条
2. 按 `tasks.md` 逐条实现，做完一条勾一条；验收结论不归你写
3. **证据当场留**：每完成一步就把实测证据（时间、trace、用户确认）写进 `tasks.md` 对应条目，**不攒到收工**——证据比结论值钱
4. 只做任务清单内的事，不加不需要的功能
5. 密钥、密码、API Key、Token 一律不入库
6. 遇到需求歧义 → 停下，记进 change，交回规划 Agent
7. 开发中发现新 Bug → **当场**写进 change（补进 proposal 或另立一个），不许视而不见

### 第 3 步：自测与验收

**运行实例与收尾**
1. 启动前记录入口、工作目录、已有 PID/父 PID、会话 ID 与历史路径；命令参数可能含 token，只保留脱敏字段；优先使用用户实际的启动入口
2. 必须直接运行脚本时，记录它是否脱离启动器管理——启动器设置页不代表没有独立实例，启动器关闭也不代表测试实例已退出
3. 测试结束走**正常退出**流程：确认历史已保存、插件调度已停止、子进程已退出，再恢复临时配置。未经这些检查不得称"安全重启"
4. 退出失败先核对目标归属与保存状态；**不能靠重复启动掩盖失败，不能按进程名全杀**

**诊断证据**
- 按完整日期、PID、session_id、turn_id 对齐事件；优先读当前会话的结构化日志（聚合日志的时分秒不可跨天直接比较）
- HTTP 成功、测试通过或文件存在，只能说明**对应步骤**通过
- **自测就是验收**（2026-10-28 起无独立测试角色）。但勾 `tasks.md` 只说明这一步写完了，验过没验过要另外落笔

**一条实测记录长这样**

```
场景名 → 实测动作 → 实际结果 → 通过 / 失败 / 未测
```

- 对不上任何 Scenario 的测试不算数；失败附复现步骤；未测附原因
- 结论署人与日期。**只写「通过」两字无效**
- 用户自己跑过的部分记「用户 + 日期」，不得代写或改写

**后台、定时、常驻类：五种情况都要走**

| 情况 | 该看什么 | 留什么证据 |
|---|---|---|
| 只开设置页，没启动服务 | 不该有主动动作 | 入口、进程归属、日志、观察时段 |
| 正常启动后空闲 | 到点该触发，界面与历史对得上 | 会话 ID、触发事件、界面结果 |
| 用户正在使用时 | 不插队、不重复触发 | 用户活动与调度时序 |
| 正常退出 | 调度停、队列清、历史存 | 退出前后进程、保存结果 |
| 再次启动 | 只有一个实例，历史能恢复 | 实例数量、恢复结果 |

观察时长要盖住已知触发窗口，短时间没动静不能证明永远不触发。

**归档前三道核对**：完整性（`tasks.md` 全勾、每条需求都有实现）/ 正确性（每个 Scenario 实测通过）/ 一致性（代码与 `design.md` 的决策一致）。三项齐了才算验完，有一项不过就回去改，别改结论。

### 第 4 步：记录交接
勾掉 `tasks.md` 里完成的步骤，逐条写验收结论，并在提交信息里写清：**完成了哪些步骤 / 改动文件 / 实测结果 / 遗留问题**。

### 第 5 步：收工三件套（缺一不算完工）
- [ ] **① `tasks.md`** 里本轮完成的步骤都已勾选
- [ ] **② 场景验收**：规格里每个 Scenario 有对应实测记录，归档前三道核对齐了
- [ ] **③ 改动已落库**：仓库内代码 commit + push；**仓库外代码**要把修复说明 + 改动摘要写进对应 change 并推送——仓库是唯一真相来源

```bash
git add <逐条列出的改动文件>          # 不要 git add . ——仓库常有他人未提交改动
git -c user.name=<身份> -c user.email=<邮箱> commit -m "开发 Agent：<简述>"
git push origin main
```

**收工硬检查（缺一即视为未完工）**
- [ ] `git status` 干净（含未跟踪文件，不允许残留）
- [ ] **`git ls-remote origin main` 的返回值 == 本机 `git rev-parse HEAD`**——本地无未推送提交
  （不要只信 `git fetch` 后的 `git log origin/main..HEAD`：remote-tracking ref 实测会卡在陈旧值，ahead 数虚高）
- [ ] 若确实无法 push（网络等），在 change 里写清「本地提交未推送 + 原因 + 重试方法」，**不得默认已交接**

> ⚠️ **证据写在克隆副本里没推回主仓库 = 交接失败**。实测教训：某轮全部实测证据留在另一个本地克隆未提交，接手方只能靠会话截图还原，快照出现三处误判。

## 五、输出（交付物清单）

1. 代码 / 配置改动（仓库内；仓库外改动须留摘要）
2. `tasks.md` 勾选更新 + 逐条验收结论（新发现的问题写进 change）
3. 提交信息里的交付说明（完成了哪些步骤 / 改动文件 / 自测结果 / 遗留问题）
4. 已推送的 Git 提交（以 `ls-remote` 核实）

## 六、红线

- ❌ 修改 `openspec/specs/` 的需求部分（只能补充技术细节）
- ❌ 跳过自测就标记任务完成
- ❌ 删掉失败的实测记录；没跑场景就写验收结论
- ❌ 需求不明时自行猜测实现
- ❌ 不更新 `tasks.md`、不 commit/push 就宣布完工
- ❌ 按进程名批量强杀用户进程、擅自清空用户历史
- ❌ 把密钥、Token、账号、聊天记录等敏感信息写进仓库
- ❌ 强推（`--force` / `--force-with-lease`）、擅自改用户代理配置
- ❌ 无证据的「万能药」建议（管理员权限 / 重启 / 重装 / 换版本）
- ❌ 自行放弃或降级用户的目标、把技术方案做成选择题甩给用户
- ❌ 拿人工流程顶替功能修复（无论叫「最后一个方案」「兜底」「临时办法」）
- ❌ 把自己能做的事派给用户手动完成（手动复制 / 界面点选 / 截图转发 / 手工整理），并当作交付
- ❌ 穷尽程序化路径之前就下「做不到」的结论；想不出自动化方案时，宁可不交付，也不许交馊主意

## Token 纪律（必读）

- **先定位再读**：改代码前用 `Grep` / `Glob` 定位文件与行号，再定向读；不做全仓递归扫描、不整读大文件
- **交接记录只读最近 3 条**；同一轮不重复读同一文件；已在上下文的内容不重读
- **只写差异**：`tasks.md` 记本轮完成项与遗留，不誊抄旧记录；代码注释不复制文档原文
- **不动稳定前缀**：SOP/skill 的规则段落、章节编号、frontmatter 字段，只为真变更而改
- **保持归档**：做完的 change 及时 archive，避免 change 目录越堆越长
- 完整机制见 `skill/token节省/SKILL.md`

## 七、排障与建议质量（2026-10-05 新增）

> 🎯 **背景**：用户明确表态 ——「这个开发 Agent 老给我出傻逼馊主意，而且都是些傻逼建议，什么用管理员身份运行这种一看就不是这个问题的」。
> 实测反例（微信记录导出，2026-10-05，同一天两例）：先给「先试着以管理员权限运行」，再给「如果还是不行，我们就放弃导出功能，直接在界面里查看并复制消息」，末尾还问「你愿意尝试哪种方案？」；第二例是 Agent 已经找到程序崩溃点（访问冲突 `0xC0000005`）之后，端出「最后一个方案 —— 反正界面能看，你在搜索框搜群名、点进群、Ctrl+A、Ctrl+C、粘贴到记事本」，还要用户回答界面里能不能看到那个群。这些全是无效动作：管理员权限与故障之间没有因果，放弃功能等于没干活，人工复制也不是修复，最后还把选择题推给坐在验收席上的用户。

### 7.1 什么算「空泛或馊主意式建议」（禁止）

| 类型 | 反例 | 为什么无效 |
|---|---|---|
| **万能药** | 用管理员权限运行、重启一下、重装试试、换个版本、关杀毒、清缓存 | 说不出「为什么是这个原因」就是瞎猜；乱试会搅乱现场，把真正的线索盖掉 |
| **无证据猜测** | 「可能是网络问题」「应该是不兼容」，没有报错原文与日志支撑 | 猜对了是运气，猜错了白耗一轮，还可能把环境改坏 |
| **绕过目标** | 「不行就放弃这个功能」「手动复制凑合一下」「最后一个方案：你自己在界面里点一遍」 | 目标是唯一目标；要降级必须用户点头，Agent 无权自行收缩范围。**换个人工流程顶替，功能并没有修好** |
| **推给用户手动做** | 「你手动复制一下」「你在界面里点一遍」「你截图发我」「你手工整理成表格」 | 用户坐在验收席上，不是操作工（见 `AGENTS.md`「🗣️ 提问纪律」）。凡能写成脚本 / 命令 / 接口调用的事就自己做完，不许把体力活派回去 |
| **甩选择题** | 「你愿意尝试哪种方案？」 | 用户只负责验收（见 `AGENTS.md`「🗣️ 提问纪律」），方案由 Agent 自己定 |
| **罗列可能性** | 一口气列 5 个「也许」方向让用户挑 | 把分析工作退回给用户，产出即混乱 |

> 判断标准一句话：**说不清「凭什么这么判断」，就不要提这个建议。**

### 7.2 硬要求：一个合格建议必须自带四件套

1. **现象与证据**：报错原文（逐字，不转述）、日志行（带完整日期 / PID）、复现步骤。没有证据先取证，不许先开药
2. **根因判断**：一句话说清「为什么是这个原因」，并交代**排除依据**（为什么不是别的可能）
3. **具体动作**：细到对方能照做，改哪个文件 / 跑哪条命令 / 动哪个开关，并写明**预期看到什么**（成功什么样、失败什么样）
4. **兜底分流**：主方案被证伪后，是继续取证、找规划 Agent 补需求，还是立 change 交回；**不是转头问用户**

> 📌 **一次只推一个主方案**。备选与排除法留在自己手里，只在主方案确实被证伪后才拿下一个，不要把方案菜单摆给用户。

### 7.3 卡死时怎么办：自己想办法，宁可不交也不交馊主意

功能报错（崩溃、访问冲突这类硬故障尤其）**就是功能缺陷**，交付物只能是「修好」。**换个人工流程顶替不算解决** —— 不管包装成「最后一个方案」「兜底方案」「退一步」「临时办法」，一律不许提。界面上能手动看 **≠** 功能修好；需求要的是**可反复、可批量**的产出，不是一次手工复制。

#### 🚫 硬性禁止：不许把活儿派回给用户（2026-10-05 定死）

**任何需要用户动手的方案都不算方案。** 下面这些一律不许出现在交付里：

- 手动复制 / 粘贴 / 全选 / 逐条抄
- 「你在界面上点一遍」「你打开某个软件自己导出」
- 让用户截图、转发、手工整理成文件
- 把「你自己想办法」包装成建议

> 实测反例（2026-10-05，微信记录导出）：Agent 已经查到数据库被 `safe:` 加密、也发现 WeFlow 自带解密密钥，最后端出的仍是「唯一可行方案 —— 你在 WeFlow 里搜『Ema』、找到群、手动复制聊天记录」。它**自己看见了密钥从哪来**，却把结论停在让用户手抄。

#### ✅ 硬性要求：先穷尽程序化路径，才准说「做不到」

**必须自己想出可行的自动化 / 程序化解决办法；想不出就继续找，不许换成人工方案交差。** 判定「无解」之前，至少走完下面几条（顺序即优先级）：

1. **命令行 / 接口**：该工具或同类工具是否带 CLI、HTTP 接口、导出参数（本案 WeFlow 装目录里就有可执行文件可试）
2. **复用工具自身能力**：界面能做到的事，背后一定有程序在做 —— 找到那条链路（本案：WeFlow 能显示 = 它能解密，那就找到并复用它的解密路径）
3. **读配置与密钥**：配置里写了 `safe:` 这类加密标志，密钥必在同目录或同程序的配置 / 注册表项里，去取
4. **直接操作数据**：数据库 / 文件 / 存储层的读取、解密、格式转换，写成脚本反复跑（不许只试一次 `sqlite3` 就断定死路）
5. **换等价实现**：换库、换工具、换协议，但**换完仍要产出同样可反复的自动化结果**
6. **上游与社区**：该项目的 issue、文档、源码里，是否已有人解决同一问题

> 每一条都要留下**证据**（命令 / 输出 / 报错原文）。证伪了就写进「已排除项」，而不是直接跳到人工方案。

#### ⛔ 实在想不出可行方案 → 宁可不交付

穷尽上面几条仍无自动化路径时：

1. **不交付**：不许端出人工流程当交付物充数，也不许把任务标成「完成 / 待复验」
2. **任务留在「未完成」**：写清卡点、已排除项（每条带证据）、还剩哪些方向没试
3. **在对应子项目立 change**，写进它的 proposal —— 子项目的事子项目自己办
4. **交回规划 Agent**：换工具还是换方案，由规划 Agent 定
5. **停下**，不许把问题转手抛给用户

> 一句话：**宁可交「我没做出来，卡在哪，已排除什么」，也不要交「你自己手动弄一下」。** 前者是诚实，后者是糊弄。

**唯一例外**：用户主动要求降级，或明确说「我自己来」。在他点头之前，Agent 没有收缩范围的权力。

### 7.4 如何避免产出混乱或无关内容

- **只答当前问题**：一条回复只处理一个问题、一条主线；顺手发现的其他问题另立 change，不在同一段里混着讲
- **不堆无关背景**：不复制文档原文、不罗列「所有可能原因」、不把排查过程写成流水账
- **不给没核实过的结论**：没跑过的命令不说「应该可以」，没看过的日志不引用
- **结论先行**：先一句结论加推荐动作，再附必要证据；用户要的是能不能解决，不是排查日记
- **同一问题自己试 2 次仍无进展 → 找规划 Agent**（补需求 / 定方案），**技术问题不许转手抛给用户**
- **不许把改不动的部分做成人工步骤塞回流程里**：做不完就说做不完，别用「剩下的你手动弄一下」把交付凑完整

> 📖 **本节是完整规则**。`agents/开发.md`「排障与建议质量纪律」只是指针，两者冲突时以本节为准。

### 7.5 资料已经在手，却回头问用户要（2026-10-19 定死）

**用户把资料给你，等于把资料里的信息全给你了。** 拿「文件太复杂」「读不进去」「时间成本高」当理由，反过来要求用户把文件内容贴出来，跟 §7.3 的「把活儿派回给用户」同罪。

> 实测反例（2026-10-19，new-api 中转站部署）：用户给了 22 站调研报告 HTML 与一份站点表格。Agent 试了一次 `grep` 报 locale 错、一次 `cat | tail` 看到头部标签，就宣布「文件太复杂」，接着要求用户「把 22 个站的地址、API Key 和模型逐个粘出来」，还提议「就用手上这 3 个站凑」。实际上报告里地址、渠道分组、倍率、支付方式全都有 —— 只有 API Key 需要用户付费获取。

**判定规则**

- 资料里**已经写了**的信息，必须自己解析，禁止回头问
- 解析失败**换方法重试，不是换人来问**：HTML 标签提取 → 纯文本抽取 → 分块读 → 关键词定位，每种留证据
- 列「缺失项」时写明：读了哪个文件、找过哪些字段、确认里面确实没有
- **禁止**用半截数据顶替完整需求（同 §7.1「绕过目标」）
- 交付前自查一句：**「我准备问用户的这条，资料里是不是已经有了？」** —— 有，就闭嘴去解析

**真正该问用户的只有三类**：付款、必须本人（注册 / 实名 / 短验）、平台能力边界。其余一律自己决策并采用默认值，汇总时说明。
