# 设计

## 为什么直接合并，而不是把测试降级成「按需调用」

先想过保留第三个角色、平时不叫它、只在后台类功能上请它出来。放弃的理由是它会把责任切开两次。

规矩挂在文件里而没人执行，是最坏的一种状态。每次归档都要问一句「这算不算要叫测试」，判断成本比干活还高，最后一定演变成看心情决定。合并之后只有一条线：谁实现谁验，验没验看证据。

## 原设计靠「换人」守住的东西，怎么补回来

原设计防的是「实现完了顺口说验过了」。它用一个独立角色的私心不存在来保证诚实，这个思路在多人团队里成立，在单人项目里是假的，因为另一个人也得靠同一份证据。

现在改成靠证据本身：验收结论必须逐条对应 Scenario，写清实测动作与实际结果。「通过」两个字不算数。这条比「换个人签」更硬，因为它可以被人复核，而签字只表示有人愿意担责。

代价是自证时容易手松。承认这一点，所以加了一道外部闸门：用户点头才归档。用户是唯一不能自己骗自己的人。

## 为什么保留后台类功能的五场景表

那张表不是测试角色的东西，是方法的沉淀。它管的是「到点有没有真触发」「关了设置页还在不在跑」「退出时队列清没清」这类靠盯进程和翻日志才能看出来的问题。

用户坐在验收席上不会去挂半小时等触发窗口，所以这类功能必须由 Agent 自己跑并留证据。表跟着手册走，进开发的手册。

## 文件怎么处置

`agents/测试.md` 与 `skill/测试Agent/` 不留在仓库里。留着就是第二种做法，以后一定有人照着它开工。

内容不丢。手册里的「怎么验」「五场景表」「归档前三道核对」并进 `agents/开发.md`；执行卡里的证据规则与红线并进 `skill/开发Agent/SKILL.md`。原文件从 git 里移除，历史可追。

## 风险

- 自证手松。靠「证据格式写死 + 用户放行」两道挡，剩下的是纪律问题，不是流程能解决的
- 已有 change（`verify-skill-assets`）的验收结论是按旧规矩写的。它本来就故意没归档，等用户看过再定，正好落在新规矩上
