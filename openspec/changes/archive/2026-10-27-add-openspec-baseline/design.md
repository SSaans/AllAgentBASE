# 设计

## 为什么根仓库也要有 openspec

这个仓库自己就是一个项目，它的「功能」是规范与流程。以前这些行为写在 BRD 的叙述段落里，改没改、改到哪一步全靠人读。给它也建 `openspec/` 之后，规范本身有了可校验的形态，改规范也得走 change，跟子项目同一套流程。

## 为什么能力名用中文

`doc-layering` 这种名字对使用者没有信息量。中文目录名实测能通过 `openspec validate --strict`，路径在 Windows 与 Git 下正常工作，仓库里本来也有 `Project/ALLBot部署` 这样的中文目录。结构标题（`## ADDED Requirements`、`### Requirement:`、`#### Scenario:`）与 `SHALL` 关键字保持英文，这是校验器认的，不能动。

## 为什么删掉 BRD 而不是留着

BRD 同时承担了需求、验收标准、子项目索引三种身份。验收标准写在散文里没法校验，索引放在 BRD 里没人维护，需求又和子项目自己的 BRD 重复。拆开之后，需求进 README，行为进 specs，索引进 README 的一张表，三样各自有了唯一主人。

## 为什么废掉 CHANGELOG

一个 change 归档后，目录里同时留下「为什么改」「改成什么样」「怎么实现的」「做了哪几步」。这四个加起来，比 CHANGELOG 那句「完成了某某功能，下一步建议某某」信息量高一个量级，而且是写 change 时顺手产出的，不需要第二次劳动。CHANGELOG 唯一还能提供的是试错过程与人际叙事，前者该进 design 的风险小节，后者没有留存价值。

代价要认下来：零碎小改动以后只有 git 提交信息，没有白话流水账。判据是这类改动占比低，且 `git log --since` 查得到。

## 为什么把三本 SOP 收进 agents/

三份手册分别是三个 Agent 的开工清单，一个 Agent 只读自己那份。放在根目录用英文名，一是看不出是谁的，二是根目录会堆。收进 `agents/` 用中文名，AGENTS.md 留公共规矩与指路，单个 Agent 的读取量降到两三百行。

## 为什么子项目各自一套 openspec

OpenSpec 认最近的 `openspec/` 根。每个子项目独立建根之后，`Project/<名字>/` 里跑命令就只作用于自己，一个项目的 change 不会污染另一个。代价是每个项目一份 `config.yaml`，可以接受。

## 风险

- **中文路径**：已在本机实测 init、new change、validate --strict 全通。若日后换到不认宽字符的工具链，回退方式是改回拼音目录名并同步引用。
- **迁移期口径混杂**：10 个子项目逐个迁，中途会有新旧结构并存。处理办法是一个项目一个提交，迁完一个删一个项目的旧文件，不留半吊子状态。
- **历史文件冻结后的查询成本**：`CHANGELOG-历史.md` 会变成千行大文件，不适合整份读。所以它的定位只是存档，日常回溯走 `openspec/changes/archive/`。
- **规则改变带来的习惯冲突**：三个 Agent 的提示词与手册同时改写，旧会话里可能还残留「写 CHANGELOG」的指令，需要用户在新会话里重新派活。
