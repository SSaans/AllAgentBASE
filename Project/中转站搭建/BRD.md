## 一、目标与范围

### 1.1 要解决的问题（现状）

现在要调 AI，是直接在某一家中转站开 key，然后把地址和 key 填进客户端。

这样带来四个麻烦：

1. **换一家站，每台客户端都要改配置**——地址、key 全得重来一遍
2. **某家站挂了、跑路、涨价，只能干等或手动切**
3. **花在哪、花了多少看不清**，各家余额分散，用量也对不上
4. **手上攒了几家的 key 之后，没法让它们互相兜底**

### 1.2 目标

搭一个自己的面板，把上面四件事一次性解决：

| # | 目标 | 判定方式（可见效果） |
|---|---|---|
| G1 | **一个固定地址 + 一个 key** 用所有模型 | 客户端只配一次，再也不改 |
| G2 | **多家上游同时挂着**，某家挂了自动切下一家 | 停用其中一家渠道，请求照样成功 |
| G3 | **用量看得见**：哪家用了多少、什么时候用的 | 面板里有调用日志与用量统计 |
| G4 | **以后加新站只动面板**，客户端零改动 | 新加一家渠道，客户端配置原封不动 |

### 1.3 本期范围

- 在本机 Windows 上把 new-api 跑起来（长期运行、重启后配置不丢）
- 接入**至少两家**上游中转站（第一家 = 用户手上正在用的那家）
- 打通客户端（Cherry Studio 为主，Claude Code / Codex 视需要）
- 能查用量、能看日志、能自己加渠道

### 1.4 本期明确不做

| 不做的事 | 原因 |
|---|---|
| ❌ 对外运营、收费、公开地址 | 用户明确「先自用」；且对外收费涉及增值电信业务资质与上游条款违约，风险等级完全不同（见 §九 R5） |
| ❌ 订阅账号逆向 / 号池 | 手上没有订阅账号；且这是 22 家站的主要封号风险来源 |
| ❌ 部署到云服务器 | 本机先跑通。要长期常驻或给朋友用时再单独立项评估 |
| ❌ 修改 new-api 源码 | 本项目只做部署与配置，不改上游代码；有改动需求另立项登记「本机改动」 |
| ❌ 接入官方直连（OpenAI / Anthropic 官方 key） | 如用户后续持有合法官方 key，走同一套渠道配置即可，无需改架构 |

## 二、底座选型：为什么是 new-api，不是 sub2api

这一步是立项时最容易搞反的地方，单独记一节。

**用户原始表述**是「做个 new-api 面板，接别的中转站」。而用户提供的调研报告里，22 家站**全部使用 sub2api 面板**。两者都是 AI API 网关，但主场完全不同：

| 维度 | **new-api** | **sub2api** |
|---|---|---|
| 上游是什么 | **API Key / 任意 OpenAI 兼容端点** | **订阅账号（OAuth 登录那种）** |
| 看家本领 | 渠道管理、负载均衡、故障转移、协议互转、私有端点纳管 | 账号池调度、粘性会话、拼车分额度、订阅配额分发 |
| 计费定位 | 按 token 计价分发额度 | 把订阅额度折算成 API 卖出去 |
| 22 家站为什么用它 | — | 他们的上游是订阅账号与逆向号池，要的正是账号池 + 拼车计费 |
| **本项目适配度** | ✅ **正好对口**——上游全是别家的 key | ❌ 没有账号来源，它最值钱的能力用不上，退化成普通聚合面板 |

**结论**：本项目底座用 **new-api**。

**sub2api 不是废弃方案，是延期方案**（见 §六 6.7）：哪天用户手上有了 Claude Max / ChatGPT Pro 这类订阅账号，想把订阅额度拆成 API 分给多个客户端用，那时 sub2api 才有价值，可以单独立项，也可以与本项目共存（sub2api 管账号池，new-api 对外发令牌）。

## 三、用户提供的调研报告怎么用

那份《sub2api 面板中转站调研报告》是**市场摸底**，不是搭建文档。它的正确用法是当**上游选站参考**，具体有三条可复用价值：

### 3.1 候选上游清单

报告入选 22 家站，共同特征是：都用 sub2api 面板、都支持支付宝/微信、都公开了渠道分组与倍率。**这 22 家理论上都能作为本项目的上游渠道**（买 key → 填进 new-api 渠道）。

### 3.2 面板识别方法（以后自己也能判断）

报告用了一套可复用的识别法，值得记下来：

- `/.well-known/ai-transit.json` 里出现 `system=sub2api` → 是 sub2api 面板
- `/api/public/transit/v1/snapshot` 能拉到公开快照 → 该站公开了分组、倍率、最低充值、可用率
- 响应头带 `x-new-api-version` → 是 new-api 系（**本项目自己搭出来就会带这个**）

### 3.3 价格与渠道基线（判断「这家是不是离谱」的尺子）

| 项 | 报告实测区间 | 读法 |
|---|---|---|
| 最低倍率 | 0.001x ~ 0.5x，主流 0.06x ~ 0.3x | 明显低于 0.06x 的，多半是限时引流或渠道不稳 |
| 充值比例 | 绝大多数「1 元 = 1 美元余额」 | 偏离太多的要看清楚计价单位 |
| 支付方式 | 全部支持支付宝/微信，多数走易支付聚合 | 只收 USDT、要求私下转账的，谨慎 |
| 渠道类型 | Kiro 逆向、CC MAX 号池、官转、Codex/GPT 号池、Grok 号池、国模 | **逆向类便宜但风险高**（封号、随时拉闸） |

### 3.4 ⚠️ 引用边界

- 报告原文声明「仅为技术调研与信息聚合，**不构成任何推荐**」——本项目同样不做推荐，只做渠道登记
- 报告数据采集于 2026-09-19，中转站价格与渠道变动频繁，**下单前必须以站内实时页面为准**
- 报告里未入选的 4 家（Stripe 已验但支付宝未确认 / 信息不足 / WAF 拦截）不视为黑名单，只是证据不足

## 四、总体架构

```
┌──────────────┐        ┌───────────────────────┐        ┌──────────────┐       ┌─────────┐
│  客户端      │        │   new-api（本机）      │        │  上游中转站   │       │  模型    │
│              │        │                       │        │              │       │         │
│ Cherry Studio├───────►│ 127.0.0.1:3000        ├───┬───►│ 渠道 A       ├──────►│ Claude  │
│ Claude Code  │ 一个   │                       │   │    │ (手上在用)    │       │ GPT     │
│ Codex        │ 令牌   │  · 渠道聚合与路由      │   │    ├──────────────┤       │ Gemini  │
│ 其他工具      │        │  · 故障转移           │   └───►│ 渠道 B       ├──────►│ Grok    │
│              │        │  · 协议互转           │        │ (后续采购)    │       │ 国模    │
└──────────────┘        │  · 令牌分发 / 用量统计 │        ├──────────────┤       └─────────┘
                        └───────────────────────┘        │ 渠道 C …     │
                                                          └──────────────┘
```

三条设计原则：

1. **客户端只看得到 127.0.0.1:3000**——上游怎么变，客户端不动
2. **同模型挂多渠道**——一个模型可以由多家站一起供，谁活着用谁
3. **只监听本机**——不对外暴露端口，这是本期安全底线（见 §八）

## 五、部署形态

### 5.1 两种方式对比

| | **方式 A：直接跑二进制（推荐先走这条）** | 方式 B：Docker Desktop + WSL2 |
|---|---|---|
| 前置依赖 | 无（SQLite 内置） | 需装 Docker Desktop 并启用 WSL2 后端 |
| 上手成本 | 下载解压即跑 | 装环境 + 拉镜像，首次较慢 |
| 资源占用 | 约 100–200 MB 内存 | 200–350 MB（new-api + PG + Redis） |
| 数据存放 | 程序目录下 `./data`（SQLite） | 挂载目录（可用 PostgreSQL） |
| 适合 | **本机自用、快速跑通** | 长期常驻、将来迁服务器 |
| 升级 | 换新 exe（需备份 data） | `docker compose pull && up -d` |

**本期推荐：方式 A**。理由是目标就一个——先跑通用起来，不该在环境上耗时间。

方式 B 留作「要长期常驻 / 给朋友用 / 迁服务器」时的下一步，届时按 §九 R7 评估。

### 5.2 关键参数（两方式一致）

| 项 | 值 |
|---|---|
| 默认端口 | `3000`（可用 `--port` 或在 compose 里改宿主机侧映射） |
| 访问地址 | `http://127.0.0.1:3000` |
| 客户端 Base URL | `http://127.0.0.1:3000/v1`（**`/v1` 不能省**） |
| 首次初始化 | 访问即进向导：设管理员账号密码 → 选**自用模式** |
| 客户端凭据 | 用「令牌管理」里创建的令牌，**不是渠道的 key**（两个东西，最容易混） |
| 数据目录 | 在仓库外固定位置（不得入库，见 §八） |

## 六、功能需求

### 6.1 渠道聚合（核心）

- 支持把**任意 OpenAI 兼容端点**登记为渠道：类型选「自定义（OpenAI 兼容）」或对应厂商类型，Base URL 填上游站的 `/v1` 地址，Key 填上游站给的 key
- 一个渠道可填多个模型（多选或通配），保存后**必须点「测试」**确认连通与延迟——不测试就上线，等于把 key 失效、地址写错的问题留到调用时才炸
- **同一模型挂多个渠道**：这是 G2 的实现方式，一家挂了自动切下一家
- 渠道可随时启用/停用/改 key，客户端零改动

### 6.2 令牌分发

- 面板里创建令牌（`sk-` 开头），可设额度、有效期、可用模型范围
- 自己用：一个令牌走全部模型即可
- 给朋友用（后续阶段）：每人独立令牌 + 独立额度，避免互相挤占
- ⚠️ 令牌与渠道 key 是两层：**令牌是发给客户端的，渠道 key 是上游给我们的**

### 6.3 协议互转

- new-api 负责在 OpenAI 格式与 Claude Messages 格式之间转换
- 实际意义：上游站哪怕只提供 OpenAI 兼容接口，**Claude Code 这类只认 Anthropic 格式的客户端也能接进来**
- 若某客户端要 Gemini 格式、Responses 格式，同样由面板转换，客户端无需适配

### 6.4 用量与日志

- 调用日志：时间、模型、渠道、token 数、耗时、成功/失败
- 用量统计：按日/按模型/按渠道看消耗
- 用途：判断哪家站更稳、更划算；发现某家 key 突然失效时能立刻定位

### 6.5 客户端接入

| 客户端 | 配置要点 |
|---|---|
| Cherry Studio | 选「OpenAI 兼容」，Base URL 填 `http://127.0.0.1:3000/v1`，粘令牌 |
| Claude Code | Anthropic 格式入口由面板提供，配 `ANTHROPIC_BASE_URL` 指向本机面板 |
| Codex / 其他 | 同上，按各自支持 OpenAI 兼容的方式填 |

### 6.6 运维动作（必须能自己完成）

- **启动 / 停止 / 查看是否在跑**
- **备份**：拷走数据目录即可（SQLite 单文件）
- **加渠道 / 换 key**：面板里点几下
- **升级**：先备份数据目录，再换新版程序

### 6.7 后续可扩展方向（本期不做，仅登记）

| 方向 | 触发条件 | 说明 |
|---|---|---|
| 上 sub2api | 用户持有订阅账号（Claude Max / ChatGPT Pro 等） | 那时 sub2api 的账号池与拼车能力才有价值，可独立立项 |
| 迁云服务器 | 需要 7×24 常驻、或给朋友稳定使用 | 本机断网/关机就没服务，这是本机方案的固有上限 |
| 对内多人分发 | 决定给朋友用 | 用令牌 + 额度实现，架构无需改动 |

## 八、边界与红线

| 红线 | 说明 |
|---|---|
| 🔴 **凭据绝不入库** | 上游站点地址、API Key、面板令牌、管理员密码，一律只存在本机程序目录与用户自己手里；文档里只写「见用户持有」 |
| 🔴 **只监听本机** | 不开放公网、不做端口转发、不上内网穿透；本期定位是自用工具 |
| 🔴 **不改上游源码** | new-api 目录是独立程序，本仓库只放文档；如确需改动，另立项并登记 |
| 🔴 **不动用户文件** | 任何删除 / 移动 / 改名（含程序目录、数据目录）先列清单报用户，拿到明确同意才动手，一律走回收站 |
| 🔴 **不提交数据目录** | 数据目录含凭据与调用记录，是用户资产，路径写在文档里即可 |
| ⚠️ **不承诺服务连续性** | 本机方案受限于开机与网络；上游站随时可能变，丢的是上游，不是我们的架构 |

## 九、风险与对策

| # | 风险 / 坑 | 影响 | 对策 | 状态 |
|---|---|---|---|---|
| R1 | **模型未配置价格会被直接拦截** | 渠道配好了，客户端一调就报「余额不足 / 未配置价格」，看着像 key 坏了 | 上线前把要用的模型都在「模型定价」里填单价；自用模式是否豁免，由开发 Agent 实测确认并记录 | 待实测 |
| R2 | **渠道测试没点** | key 失效 / 地址写错被拖到调用时才暴露 | 硬性要求：每个渠道保存后必须点测试，结果记进证据 | 流程约束 |
| R3 | **令牌与渠道 key 混淆** | 把上游站的 key 当令牌发给客户端 → 客户端报错，且泄露上游 key | 文档里把两层写清；README「首次配置」明确标注 | 文档约束 |
| R4 | **上游站跑路 / 拉闸 / 涨价** | 某渠道突然不可用 | 本期就要求挂 ≥2 家；报告里的「福利随时拉闸」这类分组不做主力 | 架构已覆盖 |
| R5 | **合规风险**（用户已问过，必须留档） | 见下方分层说明 | 本期严格限定在「自己用」；对外收费不写进规划 | 已界定 |
| R6 | **端口冲突** | 3000 被其他程序占用，服务起不来 | 改宿主机映射端口或 `--port`；先 `netstat` 查明占用者 | 已知解法 |
| R7 | 本机非 7×24 | 关机即中断；给朋友用会踩到 | 本期接受；要常驻就迁服务器（另立项，届时改 Docker + PG） | 接受 |
| R8 | 上游为活跃开源项目，本地版本会落后 | 缺新功能 | 需要时先备份数据目录再升级，不自动跟 | 接受 |
| R9 | 逆向类渠道（Kiro / 号池）稳定性差、有封号连带风险 | 渠道随时失效 | 逆向渠道只作补充、不作主力；不把鸡蛋放一个篮子 | 选站约束 |

### R5 合规风险（用户 2026-09-22 明确询问，分层留档）

| 场景 | 性质 | 实际后果 |
|---|---|---|
| 自己用 | 主要违反上游服务商条款 | 封号、断供；不涉刑事 |
| 给朋友白用 | 同上，仍是条款违约 | 同上；人少、不公开、不收费时通常无人追责，但这是「没人管」不是「合规」 |
| 对外收费运营 | 性质变化：① 上游条款违约 ② 售卖 API 额度属增值电信业务范畴，无证经营有行政处罚风险 ③ 聚合支付通道本身处于灰色地带 ④ 用户违规生成内容，责任落在运营方 ⑤ 转售未经授权的渠道（如逆向）等于在违规链条里多接一环 | 风险等级显著上升，**不建议** |
