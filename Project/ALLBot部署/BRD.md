## 项目目标

把已经能正常聊天的 AstrBot QQ 机器人（人设「丛雨」）调教成想要的样子，一共三件事：

1. **插件命令能正常用**——群里发 `/分析设置`、`/群分析`、`/群漫画` 这类指令，插件要真的响应。
2. **群总结靠指令触发**——发指令就出当天的群聊总结（话题 / 成员称号 / 金句 / 锐评），用丛雨的口气写。
3. **长回复走转发卡片**——话短就直接发；话太长（超过设定的字数）就打包成 QQ「合并转发聊天记录」卡片发出去。

后来又陆续加了一批小功能（存图、吾辈在、卡片标题、禁言、关键词回复、入群欢迎、使用说明等），规格都写在本文档第四节。

## 核心功能与技术方案

### 功能 1：插件命令正常调用（已达成）

**为什么以前 `/` 命令没反应**：命令过滤器 `astrbot/core/star/filter/command.py:191-192` **第一行就要求** `event.is_at_or_wake_command` 为真，否则直接 `return False`——命令不触发，连报错都没有。这个标志只在三种情况下为真（`pipeline/waking_check/stage.py:102-148`）：① 消息以 `wake_prefix` 里某个词开头；② @ 了机器人 / @全体 / 引用机器人的消息；③ 私聊。

**正确用法**：**@丛雨 + 不带 `/` 的指令正文**，例如 `@丛雨 sid`、`@丛雨 群分析`、`@丛雨 群漫画`。技术勘误（2026-09-16）：当前前缀不含 `/`，@ 唤醒后核心不会额外剥掉正文的 `/`；这些命令也没有带 `/` 的别名。不要靠往 `wake_prefix` 里塞 `/`——实测那样做会让群里所有 `/` 开头的消息都被当成唤醒，跟别的 bot 指令打架。

插件指令：`/群分析`、`/群漫画`、`/分析设置`、`/设置格式`、`/设置模板`、`/查看模板`、`/增量状态`。

### 功能 2：群总结（只靠指令触发，已达成）

用现成插件 `astrbot_plugin_qq_group_daily_analysis`：

- `/群分析` 出报告（话题 ≤5、成员称号 + MBTI ≤8 人、金句 ≤5、质量锐评），格式 `image + text + html`。
- `/群漫画` 出多格漫画。
- 人设要继承丛雨：`analysis_features.keep_original_persona = **true**`（设成 false 会返回 None、人设根本不加载，这是老 Bug 的根因）；`use_plugin_specific_persona = false`。
- `llm.llm_provider_id = ""` 会自动回退到当前会话模型，**不用写死**。
- `min_messages_threshold = 200` **只管定时分析**，手动发 `/群分析` 不受限。
- 定时自动分析**不启用**（用户明确要求保持关闭）。

### 功能 3：长回复走转发卡片（已达成）

**机制**：非流式回复里，所有 Plain 文本加起来**超过** `forward_threshold` 就转成 QQ 合并转发卡片（判断在 `pipeline/result_decorate/stage.py:414`：`if word_cnt > self.forward_threshold`）。**刚好等于阈值还是直发**，多一个字才转。

**前提**：QQ 档 `provider_settings.streaming_response` 必须是 `false`，否则流式结果会提前发出去、跳过这个判断。

**4.11 群漫画看不清字——待开发调优（任务 25）**

**为什么糊（有硬证据，不是猜）**：
1. 格数 = 话题数。`comic_analyzer.py:12` 的 prompt 规定「一个话题画一格」，格数取自 `analysis_features.max_topics` = **5**。
2. 出图实测只有 **1672×940**（6 张全一样）。请求的是 1792×1008（`image_size="auto"` 经 `drawing_client.py:281-282` 解析），**上游返回时缩水了**。
3. 两条一叠加：1672×940 里塞 5 格，每格宽才 ~334 像素，还得塞气泡台词和 30 字字幕 → 必然糊；QQ 再压一次更糊。

**调优处方（按效果排序，都能在 WebUI 改完热生效）**：
1. **`analysis_features.max_topics` 5 → 2 或 3**（最有效）。⚠️ 副作用：群分析报告的话题数会一起变少（同一个开关）。
2. **`image_size` 从 `auto` 改 `2k`（2560×1440）或 `1536x1024`** ——**必须实测上游是否真按这个尺寸返回**。
3. **`aspect_ratio` 从 `16:9` 改 `4:3` 或 `1:1`**（横排每格太窄）。
4. 底部字幕从 30 字压到 12 字内（属插件 prompt 改动）。
5. 验收时**必须用 QQ「查看原图」**看，别把 QQ 压缩当成插件的锅。

**4.17 聊天记录提取插件（`astrbot_plugin_chat_extractor` v1.1.0）——修复中（任务 36）**

- **要的效果（用户视角）**：把群里任意一条**合并转发**的聊天记录转给机器人（**引用转发、直接转发都行**），发 `提取 html` 或 `提取 txt` → 机器人回一个文件。html 打开后要**像 QQ 一样**：每条消息一个气泡（头像 / 昵称 / 时间），图片能直接看，**文件要显示真实文件名和大小**，视频给得出链接；聊天记录里**再套着聊天记录**时，外面是一张**能点开的卡片**（显示「共 N 条」+ 前几条预览），点一下展开、再点收起。
- **现状（2026-09-20 规划 Agent 实测）**：端到端已经通了——引用合并转发 → 解析出 8 条 → 导出 html 并发到群里（`core/data/chat_exports/` 今天共 6 个文件）。但有三个问题：
  1. **文件消息显示「未知文件（未知大小）」**：16:29 导出的 html 里出现 4 次。
  2. **没有任何能点开的卡片**：html 里 `.forward-card` 与 `toggleForward` **只出现在 CSS 和 JS 的定义里**，`onclick` 调用 **0 处** → 卡片渲染分支一次都没走到。
  3. **每条群消息都打一条 INFO 日志**（`main.py:992`）→ 日志噪音、拖慢排查。
- **字段口径（按 OneBot 接收态 + AstrBot 自身适配器的做法，照抄即可）**

  | 段类型 | 接收态字段 | 怎么拿下载链接 |
  |---|---|---|
  | `file` | 名字：`file` / `file_name` / `filename` / `name`（**`file` 最常见，现在的代码漏了它**）；大小：`file_size`；钥匙：`file_id`、`busid` | 群：`get_group_file_url(file_id, group_id, busid=102)`；私聊：`get_private_file_url(file_id)`；或 `get_file(file_id)` 直接返回 `file_name` / `file_size` / `url` |
  | `video` | `file` / `url` / `file_size` / `thumb` | 同上（有 `url` 直接用） |
  | `image` | `file` / `url` | 现状正常，不动 |

  - 依据：AstrBot 自己的适配器就是这么写的——`core/platform/sources/aiocqhttp/aiocqhttp_platform_adapter.py:254-301`：先看有没有 `url`（有就走 Lagrange），没有就按 NapCat 用 `file_id` 换 `url`；文件名按 `file_name` → `name` → `file` 依次兜底。
  - ⚠️ **群文件链接是临时的**，而且转发的记录**可能来自别的群**（那个群的 `file_id` 在当前群未必换得到链接）→ 换不到就**只显示文件名 + 大小、不给链接**，并在 html 上注明「链接不可用」。**不许因为拿不到链接就把整条消息丢掉或报错中断。**
- **卡片规格**：顶层被引用的那份合并转发**也要**渲染成卡片（**不是摊平成一片气泡**）；卡片头显示「💬 聊天记录 / 共 N 条 / 前 3 条预览」，点击展开收起、箭头翻转；卡片里的嵌套转发**递归成卡片**；嵌套段两种写法都要认（`type=forward` 取 `data.id`，`type=node` 的内容直接就是）。

#### 4.18-A 追加口径（2026-10-26 15:2x，用户第二次补充）

**① 到 180 分钟直接结束（是结束，不是截断）**
- 轮询里**先判硬上限**：`now - start >= 180 分钟` → 立刻写 `end = start + 180*60`、`duration = 180*60`、`counted = 1`，并发提示「已经到180分钟时长上限了哦！快去休息一下吧！」（@本人；文案 `hard_stop_text` 可配）。
- 这条**优先于**超时提醒：已硬结束的会话不再发「超时提醒」，也不能被 `学完了` 二次结束。
- 计划时长本来就限 180，所以 `planned=180` 的人是准点正常结束，不会落到"超"的分支。

**② 总学习时长也出列表（只列前 20）**
- 输出：
  ```
  你的总学习时长为：{minutes}分钟，数据如下：
  一共学习了{subject}{minutes}分钟！
  一共学习了{subject}{minutes}分钟！
  ```
- 头 `total_header`（`{minutes}` = **全部有效分钟总和**，不等于下面各行相加）、行模板 `total_line`、条数 `total_limit`（默认 20）均可配。
- 排序：分钟降序，同分钟按首次学习时间先后。**今日列表不设条数上限**（一般到不了 20）。

**③ 两个管理命令（不唤醒、不用 @）**

| 命令 | 作用 |
|---|---|
| `/修改技能 xx改为xx` | 把分类「xx」**改名 / 合并**成「xx」：以后照旧说旧名字，统计与展示一律算新名字 |
| `/修改今日时长 xx xx分钟` | 给**今天**的「xx」**加** xx 分钟（增量，不是改成 xx） |

- 正则：`^/?\s*修改技能\s+(.+?)\s*改为\s*(.+?)\s*$`、`^/?\s*修改今日时长\s+(.+?)\s*(\d+)\s*分钟\s*$`。**用 regex、不注册成 command**，这样 `/` 不必进 `wake_prefix`（红线：绝不往唤醒前缀加 `/`）；`/` 写成**可选**，将来万一加了前缀也不会失效。
- 「改名」**只改映射、不改历史记录**：原始 `subject` 原样保留，展示时归一 → 效果是历史一起合并，而且**能撤回**。映射要**压平**：写入 `A→B` 时，把原本指向 A 的旧别名一并改指 B，避免出现 `A→B→C` 链。
- 管理员手动补的时长**不套 5 分钟门槛**（说 3 分钟就记 3 分钟），但要计入今日 / 总列表与关键词分组。

**④ 权限：只认 AstrBot 管理员**
- 判定顺序：① AstrBot 全局管理员（`admins_id` 含该 QQ）→ 放行；② 插件配置 `admin_qq` 白名单 → 放行；③ 其余一律回「如果要改时长、请联系管理员哦！」（`no_permission_text`，可配）。
- **群主 / 群管理员不算**（用户原话「只有我这样的管理员才能改」）。
- 判定出错时 **fail-closed（一律拒绝）**，不许默认放行。

**⑤ 数据（在上一版基础上再加两张表，仍同一个 `study.sqlite3`）**
- `aliases(alias TEXT PRIMARY KEY, canonical TEXT, updated REAL)` —— 运行时改名 / 合并的映射，**优先级高于配置里的 `keyword_alias`**。
- `adjustments(id, scope, uid, date TEXT, subject TEXT, seconds INTEGER, created REAL, by_uid TEXT)` —— 管理员手动补时；`date` 用本地 `YYYY-MM-DD`，统计时并入。
- 统计口径：`有效秒 = Σ sessions(counted=1 且 duration>=300) + Σ adjustments`，再按归一后的 `canonical` 分组。

`hard_stop_minutes`(180)、`hard_stop_text`、`total_header`、`total_line`、`total_limit`(20)、`admin_qq`(list)、`no_permission_text`、`rename_ok_text`、`adjust_ok_text`。

## 管理员名单管理：三个命令 + 判定规则（2026-10-27 用户提出）

> 用户原话：「他到底判定我是管理员了吗，我怎么知道。要有 `/添加管理员 xx`、`/删除管理员 xx`、`/管理员名单` 这三个命令来确定才行」。

### 一、现在为什么"不知道"

`is_admin()` 只有一个返回值，**没有任何可见反馈**：
- 判成管理员 → 命令执行（但这本身看不出"我是因为管理员才被执行"）
- 判不成 → **静默什么都不回**（当前 bug），用户无法区分「没权限」和「插件坏了」

**所以必须给两个东西**：一个**能查名单**的命令，一个**被拒时明确开口**的提示。

### 二、两级管理员（2026-10-27 用户重定：**纯 QQ 号判定，不依赖平台**）

**🔴 关键变更**：不再问 AstrBot「你是不是全局管理员」（那条路实测走不通，`get_using_platform` 不存在）。
**改成插件自己维护两份 QQ 号名单，纯数字比对，不碰任何平台接口。**

| 级别 | 怎么认 | 存在哪 | 默认值 | 能做什么 |
|---|---|---|---|---|
| **超级管理员** | QQ 号在 `super_admins` 里 | 插件配置 `super_admins`（list） | **`["2403232967"]`（Edi）** | 全部权限 + **增删管理员** + 看名单 |
| **普通管理员** | QQ 号在 `admin_qq` 里 | 插件配置 `admin_qq`（list） | **`[]`（空）** | 改技能名 / 改今日·本周·总时长 / 看名单；**不能**增删管理员 |
| 其他人 | 两个都不在 | — | — | 拒绝，回「如果要改时长、请联系管理员哦！」 |

**判定顺序（唯一口径，纯字符串比对）**

```
① str(发送者QQ) 在 super_admins 里？ → 超管，全部放行
② str(发送者QQ) 在 admin_qq   里？ → 普管，放行修改命令，禁止增删管理员
③ 都不是                          → 拒绝，并明确回一句（不许静默）
```

**⚠️ 三条硬性约束**

1. **不许再调 `event.is_admin()` 或 `get_using_platform()`** —— 这条链路实测不可用，全部删掉。
2. **QQ 号一律按字符串比对**（`str(event.get_sender_id())`），避免 int/str 类型不一致导致判断失败。
3. **改名单必须 `save_config()` 落盘**，否则重载即丢。

### 三、三个命令的规格

| 命令 | 触发词（可配） | 格式 | 谁能用 |
|---|---|---|---|
| **添加管理员** | `添加管理员` / `加管理员` | `添加管理员 2403232967` 或 `添加管理员 @某人` 或 `添加管理员 打龙师` | **仅超管** |
| **删除管理员** | `删除管理员` / `移除管理员` / `删管理员` | 同上 | **仅超管** |
| **管理员名单** | `管理员名单` / `谁是管理员` / `管理员列表` | 直接发，不带参数 | **超管 + 普通管理员**（其他人也能看，只是名单内容不涉密） |

**指定人的三种写法都支持**（复用现有 `resolve()`）：
1. **纯 QQ 号** —— 最准，推荐
2. **@ 某人** —— 从消息段里取
3. **群里昵称** —— 走现有解析，重名时回「找到多个同名的人，请改用 @ 或 QQ 号」

**`/` 可有可无**（现有命令都这么处理）。

### 四、名单存哪里

**存插件配置**：`_conf_schema.json` 新增两项 `list` —— `super_admins`（默认 `["2403232967"]`）、`admin_qq`（默认 `[]`）。

- 改完**必须 `save_config()`**，否则重载即丢（这是老毛病，不许再犯）
- **不写 AstrBot 全局 `admins_id`** —— 那是平台级配置，插件不许越权改
- 面板里也要能直接编辑这个列表（四件套之③）

## 管理员命令不可用：根因与修法（2026-10-27 实测，三层叠加）

> 现象：群里发「修改技能 xxx 改为 xxx」「修改今日时长 xxx 1分钟」→ **完全没反应**；
> 发「总学习时长」→ 正常有回复。

### 一、根因（三层，逐条实测）

| # | 层 | 证据 | 影响 |
|---|---|---|---|
| **1** | **`is_admin()` 直接抛异常** | `main.py:348` `self.context.get_using_platform().get_admin_ids()`；日志实锤 `AttributeError: 'Context' object has no attribute 'get_using_platform'` | **所有管理员命令一进门就炸**，异常被吞 → **静默无回复** |
| **2** | **解析要求「空格」** | `rename` 正则 `\s+(.+?)改为(.+)`、`adjust` 正则 `\s+(.+?)\s+(\d+)分钟`；用真实配置跑：「修改技能打龙师改为滚木」→ **None**，「修改今日时长 打龙师1分钟」→ **None** | 少打一个空格就**完全匹配不上**（filter 不放行，连提示都没有） |
| **3** | **超大数字溢出** | 「修改今日时长 打龙师 9999…（22 位）分钟」能解析，但 `INSERT ... VALUES(?,(999999999999999999999999,))` → `OverflowError: Python int too large to convert to SQLite INTEGER` | 异常被吞 → 又一条**静默无回复** |

**对照**：查询类命令（`今日/本周/总学习时长`）走另一条分支，不需要管理员、也不写库，所以**正常**。

### 二、修法（三处，缺一不可）

**① 管理员判定改用官方事件方法**

```python
# ❌ 现在（Context 根本没这个方法）
def is_admin(self, event):
    admin_ids = self.context.get_using_platform().get_admin_ids()
    return str(event.get_sender_id()) in admin_ids

# ✅ 改成（核心 astr_message_event.py:268 提供；astrbot_plugin_mute 也是这么写的）
def is_admin(self, event):
    return event.is_admin()
```

**② 解析放宽：触发词与参数之间允许 0~N 个空格**

```python
# rename：触发词后 \s+  →  \s*
re.fullmatch(re.escape(rw) + r"\s*(.+?)\s*改为\s*(.+)", value)
# adjust：名字与分钟之间 \s+  →  \s*
re.fullmatch(re.escape(aw) + r"\s*(.+?)\s*(\d+)\s*分钟", value)
```

**③ 入参兜底：分钟数先夹紧再写库**

```python
if add_minutes < 1 or add_minutes > 1440:      # 单次上限 1440 分钟（1 天），可配
    answer = "单次调整不能超过 1440 分钟哦"
else:
    ...INSERT...
```
（避免 22 位数字直接撞 SQLite INTEGER 上限）

**④ 异常不能吞**：`handle()` 外层加 `try/except`，`logger.exception(...)` 并把错误回一句，
避免再出现「点了没反应、日志也看不出来」的情况。

## v1.3.0 需求规格：休息 / 暂停 / 放弃 / 管理员命令扩展（2026-10-27）

### 〇、状态机（所有功能都挂在它上面）

```
                 「我要学习 <科目> N分钟」          「学完了」
   IDLE ────────────────────────────────> STUDYING ──────────> REST_ASK
     ▲                                        │  ▲                 │
     │  「不学了」（作废本次）                  │  │「继续学习」      │ 发 5 / 15 / 30

     │  「不学了」（休息也一并放弃）             │                    │

**四个状态**：`IDLE`（没在学）/ `STUDYING`（学习中）/ `PAUSED`（暂停中）/ `REST_ASK`（问休息）→ `RESTING`（休息中）

### 一、管理员专属命令（4 个，仅管理员可用）

- **权限**：`event.is_admin()` 为真。**群主/群管理不算**（除非同时是 AstrBot 管理员）。
- **拒绝文案**：`admin_denied_text`，默认「如果要改时长、请联系管理员哦！」
- **边界**：单次 1–1440 分钟；超限回「单次调整不能超过 1440 分钟哦」；名字找不到回 `resolve_failed_text`。
- **落盘**：`修改技能` 改了 `keyword_alias` 后**必须 `save_config()`**，否则重载即丢。

### 二、放弃学习「不学了」

| 项 | 规则 |
|---|---|
| 触发词 | `不学了`（可配 `abandon_words`） |
| 适用状态 | `STUDYING` / `PAUSED` / `RESTING` |
| 效果 | **当前所有正在计时的会话全部作废**：`counted=0`、`duration=0`，不计入今日/本周/总时长 |
| 文案 | 「好的，这次不算了。想重新开始就说『我要学习』」 |
| 空状态 | `IDLE` 时发 → 「你现在还没有开始学习哦」 |
| 是否删记录 | **不删**，只把 `counted` 置 0（保留可追溯） |

### 三、休息功能

| 阶段 | 规则 |
|---|---|
| **触发** | `学完了` 正常结束 → **先**回「恭喜完成！这次学了 {分钟} 分钟」 |
| **询问** | 紧接着回：「要休息一下吗？回复 **5 / 15 / 30**（分钟）就行；不想休息、或者想继续学，直接说『我要学习』」 |
| **选择** | 只认 `5` / `15` / `30` 三个数字（可配 `rest_options`）→ 进入 `RESTING` |
| **休息中** | ① **禁止学习**：发「我要学习 …」→ 「先休息完再学哦，还剩 {n} 分钟」<br>② **不可暂停**：发「学习暂停」→ 「休息不能暂停哦」<br>③ 发「不学了」→ 提前结束休息，回「休息结束，随时可以继续」<br>④ 发其它数字 → 「只能回 5 / 15 / 30 哦」 |
| **结束** | 到点自动回「休息完毕，可以继续学习啦」→ 回到 `IDLE` |
| **超时兜底** | 用「定时器 + 每条消息惰性判断」双保险（重启后仍能正确恢复），同现有禁言插件做法 |
| **不休息** | 在 `REST_ASK` 阶段发「我要学习 …」→ **直接开始新学习**（不强制休息） |

### 四、暂停功能

| 项 | 规则 |
|---|---|
| 暂停触发 | `学习暂停`（可配 `pause_words`） |
| 恢复触发 | `继续学习`（可配 `resume_words`） |
| 暂停效果 | 停止累计；**暂停期间的时间不计入学习时长** |
| 恢复效果 | 从暂停点继续累计，**不重新开始** |
| 空状态 | `IDLE` 时发「学习暂停」或「继续学习」→ 「你现在还没有开始学习哦」 |
| 重复操作 | 已在 `PAUSED` 再发「学习暂停」→ 「已经在暂停中啦」；`STUDYING` 时发「继续学习」→ 「你正在学习中哦」 |
| 与休息互斥 | `RESTING` 中发「学习暂停」→ 「休息不能暂停哦」（见第三节） |

> 背景：用户反馈「claude 画的 logo 太难看」，要求**用 GPT 重画**，并且**要有丛雨的元素**。

### 二、新目标：重画一版，要好看、要有丛雨元素

**硬规格**

- **256×256，1:1，PNG**（不是 SVG 改名 —— 核心按后缀推 MIME，改名的 SVG 会裂图）
- 放插件根目录 `logo.png`，**仓库与运行目录各一份**
- **重载插件后生效**（`logo_path` 在插件加载阶段写进 metadata，刷新网页不管用）

**视觉规范（一套体系，不是各画各的）**

| 项 | 要求 |
|---|---|
| **主色** | 丛雨三个识别色：薄荷绿 `#A8D8B9`、紫 `#7B5EA7`、红 `#C1354C` |
| **画风** | 柔和渐变 + 圆角 + 细描边（日系轻量插画感），**不要扁平色块拼贴** |
| **图形** | 每张画**插件功能的抽象符号**（书 / 喇叭 / 气泡 / 钥匙 / 时钟…），**不画人物** |
| **彩蛋** | 每张角落一个**小蝴蝶剪影**（丛雨的发夹）→ 形成系列感，一眼看出是同一套 |
| **禁止** | 不要文字、不要高饱和乱撞、不要写实照片风、不要超过 3 个色相 |

**为什么不是每张都放丛雨本人**：8 个插件全用同一张脸会失去辨识度；
用「**配色 + 蝴蝶剪影**」做统一语言 —— 既统一，又处处是丛雨的痕迹。
