# 表情包同步（StickerSync）— 业务需求文档（BRD）

> 📅 立项：2026-09-20
> 👤 起草：规划 Agent（按用户指派）
> 🎯 状态：**规划完成，待用户拍板后进入开发**
> 📌 一句话：把散落各处的表情包收成「一套一包」的标准资产，存云端、按需拉取、分发给 QQ / Telegram / 微信。

## 一、目标与关键澄清

### 1.1 目标

建立一个**表情包（Sticker Pack）的统一资产库 + 云同步 + 多平台分发**体系：

1. **标准化**：每套表情 = 一个 **Pack**（目录 + `manifest.json`），格式统一、可校验、可增量更新。
2. **云端**：Pack 存 GitHub 仓库，按分类归档；换机、换地方都能拉回来。
3. **分发**：从同一份 Pack 生成各平台要的产物 —— QQ 的 `.eif`、Telegram 的贴纸包、微信的 GIF 组。
4. **前端**：本地 Web 界面管理（浏览 / 预览 / 打标签 / 一键导出 + 导入指引）。

### 1.2 ⚠️ 关键澄清（必须先对齐，否则预期会落空）

用户原话里的三个期待，**其中一个做不到、一个只能半自动、一个天然成立**：

| 用户的期待 | 实际能做到的 | 差别在哪 |
|---|---|---|
| 「要的时候拉取下载，放到 QQ 里就是收藏组」 | ⚠️ **半自动**：生成可导入的 `.eif` + 傻瓜引导（双击导入 / 选文件夹） | QQ **没有开放写入接口**，收藏是账号维度的服务端数据，第三方只能"备好包"再走 QQ 自己的导入入口 |
| 「手机也能同步，开发个手机软件？」 | ⚠️ **自研 App 属远期**（单独立项）；近期手机侧靠 **Telegram 天然云同步** + QQ 自带导入 | TG 贴纸包本身就是云端的（一个链接即装即用）；QQ/微信没有对等能力 |
| 「TG 贴纸、QQ 表情、微信表情都可以用，一套就是一个包」 | ✅ **这个抽象完全正确**，也正是本项目的核心设计 | 但**各平台的转化难度天差地别**，见下表 |

### 1.3 平台能力分级（本 BRD 最重要的结论）

| 平台 | 读取 | 写入 | 云同步 | 手机端 |
|---|---|---|---|---|
| **Telegram** | ✅ Bot API 可下载整包 | ✅ Bot API 可建包 / 加贴纸 / 排序 | ✅ **天然云端**（`t.me/addstickers/xxx`） | ✅ 原生 |
| **QQ（NTQQ，Win）** | ✅ 本地缓存目录可直接读 | ⚠️ 生成 `.eif`（**索引加密，待攻破**）或半自动引导 | ❌ 无接口 | ⚠️ 手机 QQ 支持导入 `.eif`，但需手动传文件 |
| **QQ（传统 PC 版）** | ✅ `.eif` 可解析（含分组排序） | ⚠️ 同上 | ❌ | — |
| **微信** | ⚠️ 无官方导出入口 | ❌ **无接口**，仅 PC 端「添加整套表情」手动导入 | ❌ | ❌ 只能手动 |

> **一句话结论**：**Telegram 能全自动，QQ 能半自动，微信只能"帮你备好料"**。任何声称"一键同步进 QQ/微信"的方案都是不诚实的。

## 二、QQ / TIM 表情包机制研究（用户指定调研项）

### 2.1 导出格式 `.eif`：本质是微软复合文档

`.eif`（表情导出文件）自 QQ2009 起支持，**本质是 Compound File Binary（CFB，微软复合文件格式）** —— 与老版 Office 的 `.doc` 同源容器。用 7-Zip 可直接打开看到内部结构：

```
<xxx.eif>/
├── 1Version.dat      # 版本标识（内容仅一个字符）
├── Face.dat          # ★ 表情索引（分组 + 顺序），已加密
├── Face2.dat         # 与 Face.dat 相同，疑为兼容保留
├── 0/ … 26/          # 本地自定义分组，每个目录 = 一组表情图片
└── 8213/             # 云端分组（图标为红心的那类分组）
```

关键事实：

- **图片本体没有加密** → 用现成 CFB 库（如 PyPI 的 `compoundfiles`）即可提取。
- **索引 `Face.dat` 被加密** → 想保住「分组 + 组内顺序」，必须解密它。社区已研究出算法（见「三、现成项目」的 QQEIF-Extractor 与配套 B 站专栏）。
- **分组规则**：`0–26` 是本地自定义分组；`8213` 是**云端分组**。
- **云端分组没有导出入口、也不支持排序** —— 变通办法：先导入一个含本地分组的 `.eif`，再在那个分组里选「导出全部表情」，导出物就会带上云端分组的全部内容。
- 其他相关后缀：`.eip`（旧版安装包）、`.cfc`，以及直接拿 `.zip/.rar` 当表情包。

### 2.2 本地存储位置（各端）

| 端 | 路径 |
|---|---|
| NTQQ（Windows） | `C:\Users\<用户>\Documents\Tencent Files\<QQ号>\nt_qq\nt_data\Emoji\personal-emoji\{Ori,Thumb}` |
| NTQQ（macOS） | `~/Library/Containers/com.tencent.qq/Data/Library/Application Support/QQ/nt_qq_<hash>/nt_data/Emoji/personal-emoji` |
| Android | `Android/data/com.tencent.mobileqq/Tencent/MobileQQ/<QQ号>/CustomFace`（或 `sticker`） |
| 传统 PC QQ | `C:\Program Files\Tencent\QQ\<QQ号>\CustomFace`；亦见 `Tencent Files\<QQ号>\mycollection\image` |

> 🔴 **重要否证**：`Ori` 目录是 QQ 的**缓存**，不是数据源。删掉后 QQ 重新加载收藏会把它重建 —— 也就是说，**单方面往 `Ori` 丢图片，QQ 不会把它收进收藏**。这条否掉了「直接写缓存目录」这条捷径，写入侧仍必须走 QQ 自己的导入入口。

### 2.3 原创表情（贴纸）的字节混淆

QQ 缓存的原创贴纸是**无后缀文件**，直接打开是乱码。社区已逆向出规则：

> **前 24 个字节中，偶数位字节做了 ±1 变换**（加密：偶数 −1、奇数 +1；解密反之）。按此还原即可得到正常的 GIF。

这意味着**静态与动态贴纸都能从本地缓存无损提取**（`Emoji` 目录下的静态图可直接复制，动态 GIF 需按此规则还原）。

### 2.4 数量上限（用户截图里那个「收藏空间已满」）

| 平台 | 上限 |
|---|---|
| QQ 普通用户 | **500** |
| QQ 超级会员（SVIP「表情漫游」） | **1000** |
| 微信自定义表情 | **300**（iOS 8.0.3 之后部分版本提升到 999，官方帮助中心仍写 300） |

> 💡 这个痛点**不是靠扩容解决的**，而是靠本项目的核心思路：**「云端仓库 + 按需装包」** —— 把上千张表情拆成若干主题包，用时导入、用完导出清空。上限从"天花板"变成"工作台面积"。

### 2.5 NTQQ 数据库（深水区，本项目不碰）

NTQQ 用**加密 SQLite** 存索引，密钥需从进程内存提取（社区项目 `QQBackup/qq-win-db-key`、Rust 的 `ntdb_unwrap`）。这条路能实现"程序化读写 QQ 收藏"，但**涉及进程注入与凭证提取**，本项目**明确不做**（见「八、边界与不做的事」）。

## 四、核心设计：Pack 格式（本项目的技术基石）

### 4.1 目录结构

```
packs/
└── <分类>/<pack-id>/
    ├── manifest.json      # 元数据（唯一真相来源）
    ├── cover.png          # 封面图
    ├── stickers/          # ★ 原始素材，保留最高质量
    │   ├── 001.gif
    │   ├── 002.png
    │   └── ...
    └── dist/              # 生成产物（可随时重建，默认不入库）
        ├── qq.eif
        ├── telegram/      # 512×512 PNG / WEBP
        └── wechat/        # ≤1MB GIF
```

### 4.2 `manifest.json` 字段草案

```json
{
  "id": "mo-cai-magic-girl",
  "name": "魔裁 · 魔法少女的魔女审判",
  "category": "动漫",
  "tags": ["魔裁", "魔法少女", "蓝色"],
  "source": { "type": "manual-capture", "note": "手动收集" },
  "license": "unknown",
  "cover": "stickers/001.gif",
  "stickers": [
    {
      "file": "stickers/001.gif",
      "format": "gif",
      "size": [240, 240],
      "bytes": 81234,
      "emoji": ["😭"],
      "order": 1
    }
  ],
  "targets": {
    "qq":       { "group": "魔裁" },
    "telegram": { "set": "mo_cai_by_xxxbot" },
    "wechat":   {}
  }
}
```

### 4.3 🔑 关键设计决策：**以图片为真相，把 `.eif` 当产物**

`.eif` 是**封闭二进制格式 + 加密索引**，把它当作数据源等于把命脉交给腾讯的版本更新。因此：

- **真相层** = 原始图片 + `manifest.json`（人类可读、跨平台通用、可 diff）
- **产物层** = `.eif` / TG 贴纸包 / 微信 GIF 组（可随时从真相层重新生成）
- 腾讯改格式 → 只需换一个适配器，资产零损失。

## 五、系统架构

```
┌────────────────────────────────────────────────┐
│  前端（本地 Web UI，可选 PWA 手机访问）            │
│  浏览 · 预览 · 打标签 · 一键导出 + 导入指引          │
└───────────────────────┬────────────────────────┘
                        │
┌───────────────────────▼────────────────────────┐
│  核心引擎（CLI + Python 库）                     │
│  Pack 读写 · manifest 校验 · 去重 · 格式转换        │
└───────────────────────┬────────────────────────┘
                        │
      ┌─────────────────┼─────────────────┬──────────────┐
      ▼                 ▼                 ▼              ▼
  QQ 适配器         TG 适配器          微信适配器      云端同步
  .eif 解析/生成    Bot API 建包/下载   规范 GIF 打包    Git / GitHub
  缓存目录扫描      格式转换            导入引导        索引生成
```

### 分层职责

| 层 | 职责 | 可替换性 |
|---|---|---|
| `core` | Pack 模型、manifest schema、校验、去重 | 稳定内核 |
| `converters` | 尺寸裁切、格式转换（GIF↔WEBP↔APNG↔TGS） | 依赖 ffmpeg / 专用库 |
| `adapters/<平台>` | 统一的 `export_pack()` / `import_pack()` 接口 | **每平台一个文件，平台变了只改这里** |
| `webui` | 浏览与操作界面 | 可换前端 |
| `sync` | 与 GitHub 仓库的拉取 / 推送 / 索引 | 可换后端（网盘、S3） |

### 适配器统一接口（草案）

```python
class Adapter:
    def import_pack(self, source) -> Pack: ...      # 从平台侧读取 → Pack
    def export_pack(self, pack, out_dir) -> ExportResult: ...
    # ExportResult: { artifacts: [路径], guide: "给用户看的导入步骤", auto: bool }
```

> `auto` 字段很重要：TG 返回 `True`（真·一键），QQ / 微信返回 `False`（产物 + 引导）。

## 六、实施方案（分阶段）

> 每阶段：**目标 → 交付 → 完成判据**。阶段 0 之外均待用户逐段放行。

### 阶段 0 · 立项与对齐（本轮）
- **目标**：确认需求边界（哪几个平台优先、能接受"半自动"到什么程度）。
- **交付**：本 BRD + `README.md` + `Task.md` + `CHANGELOG.md`；根 `BRD.md` 立项登记。
- **判据**：用户回复「按这个方案做」并选定首批平台（建议 **QQ + Telegram** 优先，微信降级到"备料"）。

### 阶段 1 · Pack 规范与核心引擎（无 UI）
- **目标**：把 Pack 格式定死，跑通读写与校验。
- **交付**：`manifest` schema + 校验器 + Pack 读写库；CLI：`pack init / add / list / validate / export`。
- **判据**：一次「目录 → Pack → 目录」往返，信息零丢失；非法 manifest 能被准确报错。

### 阶段 2 · 读取侧打通（先把"进得来"做扎实）
- **目标**：三条来源都能导入成 Pack。
- **交付**：① QQ 本地缓存扫描 + 后缀修正 + 原创贴纸解密；② `.eif` 解析（含分组与排序）；③ TG 贴纸包下载。
- **判据**：分别从「QQ 本地缓存」「一个 `.eif`」「一个 TG 贴纸包」各导入出至少一个合法 Pack。

### 阶段 3 · 云端同步
- **目标**：Pack 进 GitHub 仓库，换机可用。
- **交付**：仓库目录规范（分类目录）、`index.json` 索引生成器、拉取/推送流程。
- **判据**：A 机器上传 → B 机器拉取 → 可用；索引能被前端直接消费。

### 阶段 4 · 前端
- **目标**：全流程在浏览器里完成。
- **交付**：本地 Web UI（浏览、预览、标签、勾选 pack → 生成产物 → 显示导入指引）。
- **判据**：不碰命令行即可走完「拉取 → 选包 → 导出 → 按指引导入」。

### 阶段 5 · 写入侧分发
- **目标**：产物能在各平台用起来。
- **交付**：
  - TG：Bot API 一键建包（**全自动**）
  - QQ：生成 `.eif`（**若能攻破 `Face.dat` 加密回写**）；否则降级为「导出图片文件夹 + QQ 导入引导」
  - 微信：导出合规 GIF 组（≤1MB / ≤1024²）+ PC 端「添加整套表情」引导
- **判据**：TG 全自动通过；QQ / 微信 至少半自动可用，且引导步骤经用户实机验证。

### 阶段 6 · 手机侧（远期，需单独立项）
- **目标**：手机上也能用。
- **现状**：TG 侧**天然可用**（贴纸包在云端）；QQ 手机靠自带的 `.eif` 导入（手动传文件）；**自研手机 App 成本极高**，需用户明确要求后另行立项。
- **判据**：本阶段**只做评估报告**，不承诺开发。

⚠️ **本机特有约束（影响执行方式）**
1. **Bash 工具不可用**（Git Bash 损坏）→ 一律改写为 **PowerShell + Python 绝对路径**。
2. **PowerShell stdout 常不回传** → 结果写文件再读。
3. 中文路径与中文文件名必须走 **UTF-8** 明确编码，否则乱码。
4. 仓库内**禁止 `git add .`**（会带入 `data/` 敏感目录）→ 逐路径显式 add。

## 八、边界与不做的事

- ❌ **不做进程注入 / 内存读取 / 账号凭证提取**（`ntdb_unwrap` 那条路不碰）。
- ❌ **不做默认的 GUI 自动化点击**（模拟点击 QQ 界面属于侵入式，最多作为**用户显式选择**的可选项，且需另行评估合规性）。
- ❌ **不爬取 / 不传播受版权保护的表情包**；Pack 必带 `license` 字段，默认**仅私有仓库**。
- ❌ **不复制上游项目源码进本仓库**；上游仅作参考，仓库只放文档（如需引入依赖，走包管理器）。
- ❌ **不擅自删除 / 移动任何文件**（含 QQ 缓存目录）；一切删除动作先列清单并经用户明确同意。
- ❌ **不承诺"一键同步进 QQ/微信"** —— 做不到就写清楚，见「一、关键澄清」。
