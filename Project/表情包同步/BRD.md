## 一、目标与范围

### 1.1 目标

1. **标准化**：每套表情 = 一个 **Pack**（目录 + `manifest.json`），可校验、可去重、可增量更新。
2. **导出（读）**：把 TIM / 微信 里已有的收藏，提取成 Pack。
3. **导入（写）**：把 Pack 生成目标平台能接受的形态，并给出可执行的导入路径。
4. **封装包**：以上能力封装成**接口清晰、边界完备、可独立测试**的 Python 包（库 + CLI）。

### 1.2 范围（R2 修订）

| 项 | R1 初版 | **R2（本版）** |
|---|---|---|
| 平台 | QQ + Telegram + 微信 | **TIM + 微信** |
| Telegram | 作为"全自动标杆"纳入 | ❌ **移出**（用户明确「不需要再处理 Telegram」） |
| QQ 的定位 | 泛指 | ⚠️ **以 TIM 为主战场**（用户明确「你用的全是 TIM」），NTQQ 作为**次级**目标 |

> 📌 **变更留痕**：R1 关于 Telegram 的设计保留为历史记录，不再是实现目标。若日后要纳入，只需新增一个适配器实现，核心架构不变。

### 1.3 🔴 TIM 专项澄清（本版最重要的一节）

用户实际使用的是 **TIM**（腾讯办公版 QQ）。TIM 与 NTQQ（新版 QQ）**架构完全不同**，必须先分清：

| | **TIM**（用户在用） | **NTQQ（新版 QQ ≥ 9.8）** |
|---|---|---|
| 架构 | 传统 QQ 内核 | 全新重构 |
| 自定义表情存储 | ★ **`CustomFace.db` 单个数据库文件** | 图片目录 `personal_emoji\Ori` |
| 存储加密 | ✅ **未加密**（标准 CFB 格式） | 无（图片直接可读） |
| 本地表情分组 | ✅ 支持（可新建分组） | ❌ **已移除**，只能存"我的收藏" |
| `.eif` 导入 | ✅ 保留该功能 | ❌ **已移除** |
| `.eif` **导出** | ⚠️ **社区实测：导出的 eif 是损坏的** | ❌ 不支持 |
| 官方维护状态 | ⚠️ **早已停止维护** | 活跃更新 |
| 添加表情入口 | ✅ 表情面板 → 配置 → 添加表情 → **选文件 + 分组 + 快捷键** | ✅ 类似的「添加自定义表情」面板 |

#### 由此得出的三条关键结论

**① 数据源认准 `CustomFace.db`，不要走 `.eif` 往返。**
TIM 自带的「导出表情包」生成的是**损坏的 eif**，用它做中转等于把数据放在一条已知会坏的管子上。直接读 `CustomFace.db`（CFB、未加密）才可靠。

**② 写入侧有三条路径，按"风险从低到高"排序推进。**

| 路径 | 做法 | 风险 | 推荐度 |
|---|---|---|---|
| **W3 · 面板导入**（兜底） | 产出**标准化图片批次** + 引导用户在 TIM 表情面板里一次性多选导入 | 🟢 **零风险**（不碰任何数据文件） | ⭐⭐⭐ **先做这个** |
| **W2 · 直写 db** | 解析并改写 `CustomFace.db`，把表情直接写进去 | 🔴 **高**（写坏=丢表情，而"分组炸掉"正是用户的既有痛点） | ⭐⭐ 高价值但要极其谨慎 |
| **W1 · 生成 eif** | 自己构造一份**正确的** eif 交给 TIM 导入 | 🟡 中（TIM 的导入实现可能对格式挑食） | ⭐ 视 W2 结果决定 |

**③ 一切针对 `CustomFace.db` 的写操作，必须遵守"备份铁律"（见 §六）。**
用户的历史痛点就是「TIM 的表情分组经常被清空」。本项目的工具**绝不能成为新的丢数据来源**。

> ✅ **对用户的直接影响**：即使只做 W3，实际体验也是"**选一次文件夹**"（TIM 面板支持多选），而不是"点一百次"。这是可用的起点，且零风险。

### 1.4 微信侧能力

| 能力 | 状态 |
|---|---|
| 导出（读） | ⚠️ **可行但需解码**：PC 端缓存目录里是**无后缀（或 `.jojo`）的二进制文件**，需按**文件头魔数**识别真实格式 |
| 导入（写） | ❌ **无接口**：只能产出符合规格的图片组 + 引导用户在 PC 端「表情管理 → 添加整套表情」批量导入 |
| 规格硬约束 | 动态必须 **GIF ≤ 1 MB、≤ 1024×1024**；静态 JPG/PNG |
| 收藏上限 | 300（部分版本 999） |

## 二、平台机制研究

### 2.1 TIM（主战场）

#### 2.1.1 核心数据源：`CustomFace.db`

- **格式**：微软 **Compound File Binary（CFB）**，即 COM Structured Storage —— 与旧版 Office `.doc`、`.eif` 同源容器。
- **加密**：✅ **没有加密**（社区实测确认）。
- **位置**：`Tencent Files` 目录下（**具体子路径待实测确认**，见 §5.1 边界 2）。
- **结构**：CFB 内部按「目录 + 流（stream）」组织；**TIM 如何用这些流存分组与图片，公开资料尚无完整定义** → **需实测分析**（阶段 1 任务）。
- **旁证**：社区已有基于 CFB 解析的 TIM 表情解包工具（浏览器端本地处理，纯读取导出），500 MB 的库文件需约 3 倍内存 → **本项目必须流式处理**。

#### 2.1.2 `.eif` 格式解剖（备查，不作为主链路）

`.eif`（表情导出文件）自 QQ2009 起支持，本质是 CFB 容器，7-Zip 可直接打开：

```
<xxx.eif>/
├── 1Vsersion.dat     # 版本标识（内容仅一个字符）
├── Face.dat          # ★ 表情索引（分组 + 顺序 + 文件名），XOR 加密
├── Face2.dat         # 与 Face.dat 完全一致（兼容保留）
├── 0/ … 26/          # 本地自定义分组（每目录一组图片）
└── 8213/             # 云端分组（红心图标）
```

- **图片本体未加密** → 用 CFB 库即可提取。
- **云端分组（`8213`）无导出入口、不支持排序**。

#### 2.1.3 `Face.dat` 加密算法（✅ 已完全掌握，且可逆）

1. **分段**：记录之间以 `\x00\x00\x00` 分隔。
2. **加密**：每段使用 **XOR**，密钥为**单字节**，且在密文中**每隔一个字节重复出现一次**。
   - 密文形态：`[明文^K][K][明文^K][K]...`
   - 解密：`明文[i] = 密文[2i] ^ K`，其中 `K = 密文[2i+1]`
3. **密钥提取**：段内找「连续间隔 2 字节出现三次以上」的字节即为 `K`。
4. **明文字段**：含 `strFileorg` 标识，值形如 `UserDataCustomFace:<分组名>\<文件名>`。

> ✅ XOR 是对称的且 `K` 自带 → **"生成合法密文"在算法层面完全可行**。
> ⚠️ 但公开研究只逆向到「文件名」字段；其余字段（体积、索引、时间戳、图标标记）**语义未公开**，需实验补齐 → 这是 W1 路径的**唯一拦路虎**。

#### 2.1.4 其他相关路径

| 用途 | 路径 |
|---|---|
| TIM 图片缓存（群聊） | `C:\Users\<用户>\Documents\Tencent Files\<QQ号>\Image\Group` |
| TIM 图片缓存（私聊） | `C:\Users\<用户>\Documents\Tencent Files\<QQ号>\Image\C2C` |
| 传统 QQ 版图片缓存 | 同上但群聊目录名为 `Group2`（**与 TIM 不同，勿混**） |
| 自定义表情库 | `CustomFace.db`（**位置待实测**） |

#### 2.1.5 数量上限

| 账号类型 | 上限 |
|---|---|
| QQ/TIM 普通用户 | **500** |
| QQ 超级会员（「表情漫游」） | **1000** |

> 💡 用户截图中的「你的收藏空间已满，已不能添加」即命中此上限。**本项目的解法不是扩容，而是「云端仓库 + 按需装包」** —— 把上千张表情拆成主题包，用时导入、用完清空。

## 三、核心设计：Pack 格式

### 3.1 目录结构

```
packs/<分类>/<pack-id>/
├── manifest.json      # 元数据（唯一真相来源）
├── cover.png          # 封面
├── stickers/          # ★ 原始素材（保留最高质量，文件名规范化）
│   ├── 0001.gif
│   └── ...
└── dist/              # 生成产物（可随时重建，默认不入库）
    ├── tim/           # 图片批次（W3）/ 生成物（W2、W1）
    └── wechat/        # 合规 GIF 组（≤1MB / ≤1024²）
```

### 3.2 `manifest.json` schema

```json
{
  "schema_version": 1,
  "id": "mo-cai-magic-girl",
  "name": "魔裁 · 魔法少女的魔女审判",
  "category": "动漫",
  "tags": ["魔裁", "魔法少女"],
  "source": { "type": "tim-db", "account": "***123", "at": "2026-09-20T00:40:00+08:00" },
  "license": "unknown",
  "cover": "stickers/0001.gif",
  "stickers": [
    {
      "file": "stickers/0001.gif",
      "format": "gif",
      "size": [240, 240],
      "bytes": 81234,
      "sha256": "9f2a...",
      "emoji": ["😭"],
      "order": 1,
      "origin": { "platform": "tim", "group": "多终端表情漫游", "orig_name": "6LN8(4%MGL9@LHAR0AXA}(T" }
    }
  ],
  "targets": { "tim": { "group": "魔裁" }, "wechat": {} }
}
```

**字段约定**
- `schema_version` 必填，供日后升级兼容。
- `sha256` 必填 —— **去重与幂等的唯一依据**（不依赖文件名）。
- `order` 决定导入顺序；`origin.group` 保留原分组名，便于原样还原。
- ⚠️ `source.account` **留档须脱敏**（只留后 3 位）。

### 3.3 🔑 关键设计决策：**以图片为真相，把平台格式当产物**

`CustomFace.db` 与 `.eif` 都是封闭/半封闭格式，且腾讯**已在新版本移除 eif 与本地分组**。把平台格式当数据源，等于把命脉交给腾讯的产品决策：

- **真相层** = 原始图片 + `manifest.json`（人类可读、跨版本存活、可 diff）
- **产物层** = db 改写结果 / eif / 图片批次 / 微信 GIF 组（**可随时重建**）
- 腾讯改格式、换架构 → **只换适配器，资产零损失**。

## 四、封装包设计（R2 核心交付）

> 本节定义**接口规范（签名级契约）**，实现由开发 Agent 完成。目标：**调用者不必知道 TIM / 微信 的任何细节**。

### 4.1 包结构

```
stickersync/
├── __init__.py            # 公开 API（只导出稳定接口）
├── core/
│   ├── models.py          # Pack / Sticker / PlatformInfo / Capacity ...
│   ├── manifest.py        # manifest 读写 + schema 校验
│   ├── probe.py           # ★ 文件格式识别（按魔数，纯函数）
│   ├── cfb.py             # ★ CFB 容器读写（TIM 侧地基）
│   ├── naming.py          # 文件名规范化 / 长路径处理
│   └── errors.py          # ★ 异常体系
├── adapters/
│   ├── base.py            # ★ PlatformAdapter 抽象基类（契约）
│   ├── tim.py             # TimAdapter
│   └── wechat.py          # WeChatAdapter
├── sync/
│   ├── engine.py          # ★ 五阶段同步引擎（预检/计划/执行/校验/提交）
│   ├── backup.py          # ★ 备份与回滚（TIM 写入专用）
│   └── report.py          # ★ SyncReport 结构化结果
└── cli.py                 # 命令行入口
```

### 4.2 适配器契约（核心）

```python
class PlatformAdapter(ABC):
    """所有平台适配器必须实现。实现者不得抛出 errors.py 之外定义的异常。"""

    @property
    @abstractmethod
    def platform(self) -> str: ...          # "tim" | "wechat"

    @abstractmethod
    def detect(self, root: Path | None = None) -> PlatformInfo:
        """探测平台。★ 不抛异常 —— 用 PlatformInfo.available / reason 表达失败。"""

    @abstractmethod
    def list_accounts(self) -> list[Account]: ...

    @abstractmethod
    def capacity(self, account: Account) -> Capacity:
        """返回 used / limit / free，供导入前预检。"""

    @abstractmethod
    def export(self, account: Account, select: Selection,
               progress: ProgressFn | None = None) -> ExportResult: ...

    @abstractmethod
    def install(self, pack: Pack, account: Account,
                *, dry_run: bool = False) -> InstallResult:
        """★ dry_run=True 时只出计划、不落盘。"""
```

**契约要点**
1. `detect()` **不抛异常** —— 探测失败是常态（未安装），用返回值表达。
2. **所有写操作必须支持 `dry_run`**。
3. 单个素材失败**不得中断整批** —— 收集进结果对象。
4. 实现类**不得抛出** `errors.py` 之外的异常类型。

### 4.3 数据模型（不可变）

```python
@dataclass(frozen=True)
class Sticker:
    path: Path; format: str; size: tuple[int, int]; bytes: int
    sha256: str; order: int; emoji: tuple[str, ...] = ()

@dataclass(frozen=True)
class Capacity:
    used: int; limit: int
    @property
    def free(self) -> int: return max(0, self.limit - self.used)

@dataclass(frozen=True)
class PlatformInfo:
    platform: str; available: bool; version: str | None
    root: Path | None; reason: str | None      # available=False 时必填
```

### 4.4 异常体系

```
StickerSyncError                         # 基类
├── PlatformNotAvailable                 # 未安装 / 版本不支持 / 根目录未找到
├── AccountAmbiguous                     # 多账号且未指定
├── AccessDenied                         # 无读写权限 / 被占用
├── PackInvalid                          # manifest 不合法 / 与文件不一致
├── AssetUnreadable                      # 图片损坏、0 字节、无法识别格式
├── AssetTooLarge(found, limit)          # 超出平台体积 / 尺寸限制
├── QuotaExceeded(need_free, free)       # 收藏容量不足
├── ResourceBusy                         # 文件锁冲突 / 目标被其他进程占用
├── BackupFailed                         # ★ 备份失败 → 拒绝任何写操作
└── DataIntegrityError                   # ★ 改写后校验不通过 → 已回滚
```

**原则**：异常只用于**「整体无法继续」**；**「部分失败」用结果对象表达**，不抛异常。

### 4.5 同步引擎：五阶段

```
① 预检 Precheck   → 只读。平台可用？账号明确？容量够？素材合法？备份可写？
                    ✗ 不通过 → 直接返回 Rejected（附原因），不落任何盘
② 计划 Plan       → 生成"将要做的事"清单（入哪些、跳哪些、为什么）
                    ✗ dry_run 到此为止
③ 备份 Backup     → ★ 仅当目标为 TIM db 时：强制备份（带时间戳），失败即中止
④ 执行 + 校验     → 写【临时副本】→ 校验（数量/大小/可解析）→ 原子替换
                    ✗ 任何一步失败 → 用备份回滚
⑤ 报告 Report     → 输出 SyncReport（ok / skipped / failed，各带原因）
```

### 4.6 结果报告

```python
@dataclass(frozen=True)
class InstallResult:
    ok: list[str]          # 成功项
    skipped: list[Skipped] # 已存在 / 不符合规则（带原因）
    failed: list[Failure]  # 失败项（带异常类型与消息）
    plan: list[str]        # 本次实际执行的动作
    backup_path: Path | None = None   # ★ TIM 写入时必填
    @property
    def status(self) -> str: ...      # "ok" | "partial" | "failed"
```

**可读性要求**：`skipped` / `failed` 每条必须带**人类可读原因**，而不是裸异常字符串。

## 五、边界情况与处理策略

> 本节是「逻辑严谨、稳定可靠」的落点。**每条都必须是可测试的用例**。编号供测试 Agent 回指。

### 5.1 TIM 侧

| # | 边界情况 | 处理策略 |
|---|---|---|
| 1 | TIM 未安装 / 根目录不存在 | `detect()` 返回 `available=False` + 原因；不抛异常 |
| 2 | **`CustomFace.db` 实际路径不确定** | ★ 多候选路径探测 + 全盘受限搜索（`Tencent Files` 下按文件名匹配）+ **允许手动指定**并记住 |
| 3 | 存在多个 QQ/TIM 账号 | 列出全部；未指定时抛 `AccountAmbiguous`；CLI 提供交互选择 |
| 4 | TIM 正在运行、db 文件被占用 | 读通常可行；写操作捕获占用 → 重试 3 次（指数退避）→ 仍失败抛 `ResourceBusy`，提示「请退出 TIM 后重试」 |
| 5 | **图片后缀与实际格式不符**（GIF 被存成 `.jpg`） | ★ **一律按文件头魔数判定**，不信任后缀 |
| 6 | 文件 0 字节 / 头损坏 | 跳过并计入 `failed`（`AssetUnreadable`），**不中断整批** |
| 7 | db 内图片名与真实内容无对应关系 | 以**内容 sha256** 为准；原名仅作 `origin.orig_name` 留档 |
| 8 | **db 结构超出已知范围**（新增流/字段） | ★ **只读模式降级**：未知结构不猜测、不写入，明确报"结构未知，已跳过写入" |
| 9 | 收藏容量不足 | 导入前调 `capacity()` 预检 → 不足抛 `QuotaExceeded(need_free=N)`，消息写明「需先腾出 N 个位置」 |
| 10 | 同一表情重复收藏 | 按 `sha256` 去重；已存在的计入 `skipped`（幂等） |
| 11 | 文件名含非法字符 / 路径超 Windows 260 | 规范化 + 截断 + 加短哈希后缀，保证唯一可寻回 |
| 12 | 中文路径 / 中文分组名 | 全程显式 UTF-8；不依赖系统默认编码 |
| 13 | 混合格式（GIF + PNG + JPG 同批） | 全部支持；导出时按格式归类 |
| 14 | **写 db 前** | ★ **强制备份**（`CustomFace.db.bak-<时间戳>`）；备份失败 → 抛 `BackupFailed`，**拒绝写入** |
| 15 | **写 db 后** | ★ 重新解析校验（分组数、表情数、可读性）→ 不通过则**自动回滚**并抛 `DataIntegrityError` |
| 16 | db 文件很大（数百 MB） | 流式处理，禁止一次性全读进内存；进度回调 |
| 17 | 磁盘空间不足 | 预检可用空间（含备份体积），不足则拒绝 |
| 18 | NTQQ（无本地分组、无 eif） | 走"图片批次 + 面板导入"，**不得**声称已自动导入 |

### 5.2 微信侧

| # | 边界情况 | 处理策略 |
|---|---|---|
| 19 | 缓存目录路径随版本变化 | 多路径探测（≥3 候选）+ 手动指定 |
| 20 | 文件**无后缀 / `.jojo`** | 按魔数识别（GIF / PNG / JPG / WEBP / APNG） |
| 21 | **GIF > 1 MB** | 用 ffmpeg 降帧 / 降尺寸压缩到限值内；不可压缩时归入 `failed` 并说明 |
| 22 | 尺寸 > 1024×1024 | 自动等比缩放；**保持宽高比**，不拉伸 |
| 23 | 微信不认的格式（APNG / WEBP） | 转换为 GIF |
| 24 | 收藏已达上限 | ⚠️ **微信无接口可探测剩余容量** → 明确标注"无法预检，需用户自查" |
| 25 | 静态图带透明通道 | 微信静态表情不接受透明 → 合成白底后导出 |
| 26 | 多个微信账号目录 | 列出 + 指定 |

### 5.3 通用

| # | 边界情况 | 处理策略 |
|---|---|---|
| 27 | `manifest` 与实际文件不一致 | `PackInvalid`，指明具体哪个文件缺失 / 大小不符 |
| 28 | 磁盘空间不足 | 预检（产物体积 + 备份体积），不足则拒绝并给出所需空间 |
| 29 | 过程中被中断（Ctrl+C / 崩溃） | 临时文件 + 原子替换 → **不留半个包**；残留临时文件下次启动清理 |
| 30 | 同 Pack 重复导入 | 幂等：按 `sha256` 跳过已存在项 |
| 31 | 同一目标被并发操作 | 目标加**文件锁**；冲突抛 `ResourceBusy` |
| 32 | 素材数量超出平台单次处理能力 | 自动**分批**，逐批提交并汇总报告 |
| 33 | 空 Pack / 只有封面的 Pack | `PackInvalid`，拒绝执行 |
| 34 | 记录导出时间 | 统一带时区 ISO 8601；不写裸本地时间 |

## 六、稳定性与安全设计原则

| 原则 | 落地要求 |
|---|---|
| **先读后写** | 写操作前必须完成只读预检；预检不过**一个字节都不落盘** |
| 🔴 **备份铁律** | **任何对 `CustomFace.db` 的写入，必须先自动备份**（带时间戳、独立目录）；备份失败即中止。用户的历史痛点就是"TIM 表情分组被清空"，本工具绝不能成为新的丢数据来源 |
| **副本改写** | 绝不原地修改：读原 db → 生成新副本 → 校验 → 原子替换 |
| **可回滚** | 保留最近 N 份备份，提供一键回滚命令 |
| **可预演** | 所有写操作支持 `dry_run`，输出人类可读计划 |
| **原子性** | 写临时文件 → 校验 → 原子重命名；失败整体回滚 |
| **幂等** | 以 `sha256` 为准，重复执行结果一致 |
| **隔离失败** | 单个素材失败计入报告，不影响其余素材 |
| **不猜** | 后缀不可信、路径不可硬编码、容量不可假设、**未知结构不猜测** |
| **可复现** | 结构化日志（文件 + 控制台），记录「做了什么、跳过什么、为什么」 |
| **不越权** | 不注入进程、不读内存、不提取账号凭证（见 §九） |

- **判据**：**经用户实机导入成功**；§5 中 9–15、21–25 各有用例覆盖。
- ⚠️ W2 未通过验证前，不得发布任何会写 db 的功能。

### 阶段 4 · 同步引擎与健壮性
- **交付**：五阶段引擎 + `SyncReport` + 备份/回滚 + 锁与原子替换 + 中断恢复。
- **判据**：§5「通用」8 条全部有用例；模拟中断与模拟写入失败后，**数据必须完好**。

### 阶段 5 · 前端
