## 一、目标与范围

### 1.1 目标

1. **提取**：把各平台客户端里的聊天记录取出来（本地数据库解密 / 服务端接口拉取）。
2. **归一**：各平台原始数据 → **统一消息模型**，屏蔽平台差异。
3. **导出**：统一模型 → 可读、可长期保存的格式（HTML 为主，兼 CSV / TXT / Markdown / DOCX / XLSX / JSON）。
4. **检索与衍生**：跨平台全文检索、统一时间轴、年度报告、AI 语料。

### 1.2 范围（当前阶段）

| 阶段 | 平台 | 状态 |
|---|---|---|
| **当前（S0）** | 微信（3.x） | 引擎已落地，链路已跑通（结论待正式复验） |
| 下一步（S1） | —— | 架构整改：抽统一模型与引擎接口 |
| 规划中（S2） | QQ / TIM | 未启动 |
| 规划中（S3） | B 站私信 → 抖音私信 | 未启动，抖音定位探索 |
| 远景（S4） | 跨平台统一检索 / 时间轴 / 年度报告 | 未启动 |

### 1.3 🔴 边界（不可越）

| # | 边界 | 说明 |
|---|---|---|
| B1 | 只处理**本人账号、本人登录设备**的数据 | 不做他人账号、他人设备 |
| B2 | 不做群成员批量抓取 | 只导出自己有权限看到的会话 |
| B3 | **不提供「找回已删除消息」** | 服务端不留存，技术上做不到；宣称能做到的都是骗局 |
| B4 | 原始数据库**全程只读** | 引擎不得改写微信/QQ 的任何数据文件 |
| B5 | **仓库只存代码，永不存聊天记录** | 解密后的数据库与导出产物必须在仓库之外 |
| B6 | 不做任何形式的数据上传、分享、出售 | —— |

## 三、总体架构

```
┌──────────────────────────────────────────────────────────┐
│ ① 采集层 Collectors     每个平台一个引擎                  │
│     微信 / QQ / TIM / B站私信 / 抖音私信 …                │
│     职责：定位数据 → 取密钥 → 解密 / 拉取 → 原始记录       │
├──────────────────────────────────────────────────────────┤
│ ② 解析层 Parsers                                          │
│     职责：原始字节 → 平台语义（文本/图片/语音/引用/合并转发）│
├──────────────────────────────────────────────────────────┤
│ ③ 统一模型 Unified Model   ★ 全项目枢纽 ★                 │
│     Message / Contact / Conversation / Attachment         │
├──────────────────────────────────────────────────────────┤
│ ④ 导出层 Exporters        完全平台无关，只吃统一模型       │
│     HTML / Markdown / CSV / JSON / TXT / DOCX / XLSX      │
├──────────────────────────────────────────────────────────┤
│ ⑤ 应用层 Apps                                             │
│     跨平台检索 / 时间轴 / 年度报告 / AI 语料               │
└──────────────────────────────────────────────────────────┘
```

### 🔑 唯一真正需要守住的纪律

> **第 ④ 层永远不知道数据来自哪个平台。**

只要守住这条，新增一个平台就只是"再写一个 ①② 层引擎"，导出能力自动继承；
一旦破例（导出层里出现 `if 平台 == 'wechat'`），项目就退化成"一堆抓取脚本的合集"，
后续每加一个平台都要重写一遍导出。**这是本项目的技术主张，也是 S1 必须先做的原因。**

## 五、平台优先级与阶段性目标

### 5.1 优先级表

| 平台 | 数据在哪 | 技术路径 | 技术可行性 | 优先级 |
|---|---|---|---|---|
| **微信** | 本地加密 SQLite | 读进程内存取密钥 → 解密 | **高** | **P0** |
| **QQ (NT)** | 本地加密 SQLite | 逆向 NT 数据库密钥 + 结构解析 | 中 | **P1** |
| **TIM** | 本地加密 SQLite | 与 QQ 同内核，引擎复用 | 中 | **P1（与 QQ 同批）** |
| **B 站私信** | 无本地存储 | 登录态 + 接口翻页拉取 | 中低 | P2 |
| **抖音私信** | 无本地存储 | 接口 + 签名 + 强风控 | 低 | P3 |

### 5.2 判断依据（为什么是这个顺序）

- **QQ / TIM 放 P1 —— 性价比最高**：两者是同一个 NT 内核，数据格式、加密方式、目录结构高度相似。
  **做 QQ 等于顺带做了 TIM。**
  ⚠️ 但必须认准一条：社区流行的 NapCat / Lagrange 这类"协议端"能通过 OneBot 接口拉消息，
  但它们拿的是**服务端保留的历史**——腾讯服务器不长期保存聊天记录，所以**拿不全**。
  要拿完整历史，**仍然必须解密本机 NT 数据库**，这条路绕不过去。

- **B 站私信放 P2（不是 P3）—— 它其实是除 QQ 外最容易的**：私信历史保存在**服务端**且可通过接口翻页拉取，
  **不需要本地逆向**。真正的难点不是技术，而是两件事：接口非公开、随时可能变更；请求频率过高会触发风控。
  用户判断"短期希望较低"主要来自这两点——**这个谨慎是合理的**，但从技术难度上它确实排在抖音之前。

- **抖音放 P3 —— 长线探索，不承诺**：接口签名（X-Bogus / a_bogus / msToken 那套）复杂、
  风控最强、且纯爬虫属性带来的合规风险最高。**不作为任何阶段的交付承诺。**

### 5.3 阶段目标

| 阶段 | 目标 | 验收标准 |
|---|---|---|
| **S0** | 微信引擎落地，HTML 导出可用 | 能导出真实会话的 HTML，浏览器正常浏览（图文视频齐全） |
| **S1** | 抽统一模型与引擎接口，导出层平台无关 | 微信 HTML 输出与改造前等价；新增引擎只需实现接口 |
| **S2** | QQ + TIM 引擎 | 能解密本机 NT 数据库，导出文本 / 图片历史 |
| **S3** | B 站私信；抖音可行性结论 | B 站：能翻页拉取并导出；抖音：产出"能做 / 不能做"的明确结论 |
| **S4** | 跨平台统一检索 / 时间轴 / 年度报告 | 一次搜索命中所有平台的记录 |
