## 一、目标与范围

### 1.1 目标（收窄后）

**只做一件事：把微信聊天记录导出成可用、可长期保存的格式。**

1. **取出**：解密微信本地数据库，拿到原始聊天记录。
2. **解析**：把原始字节还原成消息语义（文字 / 图片 / 视频 / 语音 / 文件 / 引用 / 合并转发）。
3. **导出**：输出成可读格式。**HTML 为主**，兼 CSV / TXT / Markdown / DOCX / XLSX / JSON。
4. **可用**：能按联系人、群聊、时间范围筛选；能批量导出；产物能在浏览器里正常浏览。

### 1.2 范围

| 项 | 内容 |
|---|---|
| **平台** | ✅ **只有微信**。其余平台一律不做 |
| **客户端** | 以**微信 4.x** 为主战场（本机已是 4.x）；3.x 作为历史能力留档、**不投入** |
| **数据来源** | 本机微信客户端数据库（解密后读取） |
| **使用场景** | 本人、本机、离线导出 |

### 1.3 🔴 明确不做（2026-10-05 移出范围）

> 以下原属本项目早期的「跨平台归档」设想，**用户已拍板收窄，全部移出范围**。
> 原文保留在本文档历史版本与 `CHANGELOG.md` 里，**留档不改写**。

| 已移出 | 说明 |
|---|---|
| ❌ QQ / TIM 引擎 | 原 P1 计划，撤销 |
| ❌ B 站私信提取 | 原 P2 计划，撤销 |
| ❌ 抖音私信 | 原 P3 计划，撤销 |
| ❌ 「统一消息模型」枢纽层 | 原为屏蔽多平台差异而设，**单平台后不需要这层抽象** |
| ❌ 跨平台检索 / 统一时间轴 / 年度报告 | 原 S4 远景，撤销 |
| ❌ 多平台引擎接口与插件化 | 撤销，**不为未来的平台预留抽象** |

> 📌 **收窄的技术后果**：架构从「五层 + 统一模型枢纽」简化为「**解密 → 解析 → 导出**」三层直连。
> 少一层抽象，代码更短、更好懂、更好维护。**这是收窄的收益，不是损失。**

### 1.4 🔴 边界（不可越）

| # | 边界 | 说明 |
|---|---|---|
| B1 | 只处理**本人账号、本人登录设备**的数据 | 不做他人账号、他人设备 |
| B2 | 不做群成员批量抓取 | 只导出自己有权限看到的会话 |
| B3 | **不提供「找回已删除消息」** | 服务端不留存，技术上做不到；宣称能做到的都是骗局 |
| B4 | 原始数据库**全程只读** | 引擎不得改写微信的任何数据文件 |
| B5 | **仓库只存代码，永不存聊天记录** | 解密后的数据库与导出产物必须在仓库之外 |
| B6 | 不做任何形式的数据上传、分享、出售 | —— |

## 三、总体架构（单平台版）

```
┌──────────────────────────────────────────────────────────┐
│ ① 解密 Decrypt                                            │
│     定位微信数据目录 → 取密钥 → 解密数据库                 │
├──────────────────────────────────────────────────────────┤
│ ② 解析 Parse                                              │
│     原始字节 → 消息语义（文字/图片/视频/语音/文件/引用/转发）│
├──────────────────────────────────────────────────────────┤
│ ③ 导出 Export                                             │
│     HTML（主） / Markdown / CSV / JSON / TXT / DOCX / XLSX │
└──────────────────────────────────────────────────────────┘
```

### 🔑 收窄后唯一要守住的纪律

> **导出层不碰数据库，只吃解析层给的结构化消息。**

这条与原「导出层平台无关」同源，但要求更低。**不再需要为多平台做抽象**，
只要保证「解析」与「导出」之间有一层干净的数据结构即可 —— 这样加导出格式不用动解密与解析。

## 五、当前现状（2026-10-05 实测，全部脱敏）

### 5.1 环境

| 项 | 实测结论 |
|---|---|
| 微信版本 | **4.x** —— 与本项目立项时的 3.x **不是同一代产品** |
| 微信运行状态 | ✅ 正在运行 |
| 3.x 客户端 | ❌ 已不在本机 |
| 3.x 数据目录 | ⚠️ 已空，**旧版本的聊天数据不在本机** |
| 4.x 数据目录 | ✅ 存在，结构为 **4.x 的标准布局**：账号目录下是 `db_storage`，再分 `contact` / `message` 等子库 |
| 4.x 数据目录（第二份） | ⚠️ 另有**一份落在下载区** → **需确认哪份是当前生效的** |

### 5.2 🔴 关键结论：3.x 的老成果不能直接搬

- 立项时跑通的是 **3.x 链路**（本地加密库 → 取密钥 → 解密 → 导出 HTML）。
- 本机现在只有 **4.x**，其**数据库结构、目录布局、密钥获取方式都变了**。
- ⇒ **§八 的功能验收必须在 4.x 上重新跑**，旧结论一律不适用。

### 5.3 🔴 4.x 链路当前状态：未跑通（有失败证据）

- 开发 Agent 在 2026-09-29/30 试过 4.x 路线（用上游的 4.x 解密与解析模块），**流程走完但结果是坏的**：
  解密产物在解析阶段报 **`sqlite3.DatabaseError: file is not a database`** —— 产出的文件不是合法 SQLite。
- 含义：**要么密钥没取对，要么解密步骤没真正生效**。这条链路的**第一环就断了**。
- ⚠️ 相关临时脚本散落在**仓库根目录且未入库**，指向的输出目录**已不存在** →
  这批尝试**没留下可复现的证据**，属**交接缺口**（对策见 §六 `R5`）。

### 5.4 ⚠️ 部署载体缺失（必须核实）

- 立项时承载部署的那个**私有仓库工作树，在本机已不存在**；旧的解密产物目录也已不存在。
- 🔴 **本规划 Agent 无法确认它是有意清理还是意外丢失** —— **不作猜测**，列为待用户核实项（见 §九）。
- 另：远端那个私有仓库是否还在、是否仍为 private，**本轮因凭据审批未通过而未能核实**，同样列为待核实。
