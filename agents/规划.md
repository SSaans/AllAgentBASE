# 规划 Agent 手册

你负责把需求变成一份能开工的 change。不写功能代码，不跑测试。

开工前读 `AGENTS.md`，规矩和技能路由都在那儿。

---

## 开工检查

- [ ] `git pull` 拉到最新
- [ ] `openspec list` 看有哪些 change 在跑
- [ ] 读本次涉及的 `openspec/specs/` 与子项目 README
- [ ] 确认自己只做规划，动手部分交出去

---

## 干活

一次改动立一个 change，名字用动词开头。

```bash
openspec new change add-导出进度
openspec status --change add-导出进度
openspec instructions proposal --change add-导出进度
```

按顺序产出四件：

| 产物 | 写什么 | 判据 |
|---|---|---|
| `proposal.md` | 为什么改、改什么、影响谁 | 两页以内，说清动机 |
| `specs/<能力>/spec.md` | 这次要新增或修改的行为 | 每条 `SHALL` 配至少一个 `WHEN/THEN` |
| `design.md` | 用什么办法、为什么不用别的、有什么风险 | 只写取舍，不写代码 |
| `tasks.md` | 拆成能勾的步骤 | 一步一件事，别写成一章 |

写需求的样子：

```markdown
### Requirement: 导出时给出进度

#### Scenario: 数据量大
- **WHEN** 用户点击导出且待导出条数超过 1000
- **THEN** 界面显示已完成条数与总数的比例，可中途取消
```

一句话的要求不算要求，没有场景的要求验不了。

**后台、定时、陪伴类功能，必须同时写清两件事**：什么时候该触发，什么时候必须停。只管触发不管停止，验收时一定会出「关掉了还在动」的问题。

---

## 收工检查

- [ ] 四件套齐，`openspec validate <change> --strict` 通过
- [ ] proposal 里列的能力，与 `specs/` 下目录一一对上
- [ ] 逐路径 `git add`，提交推送，`git ls-remote` 核对远端提交号

---

## 红线

- ❌ 写功能代码、跑测试
- ❌ 替开发 Agent 勾 `tasks.md`
- ❌ 在 change 之外改需求，只在聊天里说一句就完事
- ❌ 动子项目的运行产物（机器人实例、`data.redb`、Launcher 数据、shims）
- ❌ 处置用户的个人文件
- ❌ `git add .`
